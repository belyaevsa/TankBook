**FENCE 1 – Do NOT cross-verify Ed25519 between languages.** Ed25519 is a standardised, fully
specified signature scheme (RFC 8032). CryptoKit's `Curve25519.Signing.PublicKey.isValidSignature(_:for:)`
and BouncyCastle produce and accept identical signatures. There is nothing to investigate here. A previous
run spent an entire budget on this and delivered nothing. Use CryptoKit, write a test with a fixed
known-good keypair + document + signature triple, and move on.

**The real cross-language risk is canonicalization, not the curve.** The signature is computed over
`ConfigCanonicalizer.Canonicalize(documentJson)` output. Rule 5 – numbers are emitted as their *source
token* via `GetRawText()`, never re-serialized from a parsed Double – is the one place a naive Swift
implementation will diverge, because `JSONSerialization` will happily turn `0.75` into `0.75000000000000001`
or `1e3` into `1000`. Spend your care there. Concretely: parse the served document bytes yourself,
preserving number tokens verbatim as substrings; do not round-trip numbers through `Double`.
Note you already have a `JSONValue` type at `ios/Sources/TankbookCore/Sync/JSONValue.swift` – read it
first and check whether it preserves raw number tokens. If it does not, either extend it or write a

## The wire contract you consume

`GET {baseURL}/v1/config`, **public, no auth**, returns:

```json
{ "document": { ...the config document, verbatim... }, "signature": "<base64>", "version": 3 }
```

- `ETag` is sent on every 200; send it back as `If-None-Match` and handle `304 No Content-body` by
  keeping the cached document and refreshing only `fetchedAt`.
- `503` with a problem+json body means the server has no published document → keep cache / bundled.
- The signature is over the **canonical bytes of `document`**, base64-encoded.
- There is also `GET /v1/config/public-key` returning `{ keyId, publicKey }`. **Do not use it to obtain
  the verification key at runtime** – that would defeat the entire threat model (an attacker who can move
  `apiBaseUrl` would serve their own key). The public key is **bundled in the binary**. The endpoint exists
  for operational tooling only. Say so in a comment so the next reader does not "fix" it.

## What to build

### 1. Bundled defaults
`Config.default.json` as a package resource (`.process` resource in `Package.swift` – you will need to add
a `resources:` entry to the `TankbookCore` target). Must be complete and always valid: every required key
in `config.schema.json` present. `apiBaseUrl` is the compiled-in production default. A build-time-verifiable
test asserts the bundled default parses and resolves.

### 2. Atomic cache file
`Application Support/Tankbook/config.cache.json`, shape per CONFIG.md §"Where it is stored":
`{ document, signature, etag, fetchedAt, activeBaseURL, consecutiveFailures }`.

- Store the **raw document verbatim** – the exact bytes served, not a re-encoded form. A future build must
  be able to read keys this build does not know about, and the signature only verifies over the served bytes.
- Write atomically: temp file → `FileManager.replaceItemAt` / rename. A crash mid-write must never leave a
  truncated document.
- File protection `.completeUntilFirstUserAuthentication` (same class as the database).
- `URLResourceValues.isExcludedFromBackup = true`. This removes the backup-tamper vector outright.
- Must be readable **before** GRDB opens, and must survive a failed database migration. So: no GRDB
  dependency in this path.

### 3. Three-layer resolver
Precedence per CONFIG.md §"How it is resolved": Debug override (DEBUG builds only, compiled out of Release)
> Remote (live, else cached) > Bundled default.

Two rules operate at two levels and conflating them is the classic bug – get this right and test both:
- **Document level: all or nothing.** Malformed / unsigned / badly-signed / expired / below-floor / older
  version → reject the *entire* document, fall to the layer beneath. Never partially applied.
- **Key level: sparse override.** Once a document is valid, each key it *contains* overrides the layer
  beneath, per key. A document setting only `tier3CloudFallback` changes exactly that and nothing else.
- Unknown keys: ignored for resolution, **retained in the cache**.

### 4. Typed `AppConfig` + injected `ConfigStore`
Use the shape given in CONFIG.md §"How code consumes it" (`AppConfig` struct, `@Observable ConfigStore`
with `current`, `snapshot()`, `isEnabled(_:)`, `refresh()`). Three rules:
- Snapshot at the start of an operation, used throughout – no live per-call-site reads.
- Typed fields, not string keys. Add a coverage test asserting every remote-configurable key documented in
  CONFIG.md §"What may be configured remotely" maps to a field.
- **Injected, not a singleton** – tests must construct a `ConfigStore` over fabricated layers with no file
  and no network. Inject the filesystem location, the clock, and the HTTP transport as protocols.
  A hard-coded `Date()` or `URLSession.shared` in this code is a defect: expiry and rollback tests need a
  controllable clock.

### 5. Ed25519 verification ON EVERY CACHE READ
Not only at fetch. This is the whole game – validating at fetch and then trusting the cache bypasses
signing entirely. Verify on every read **including the read on cold start**. CryptoKit, bundled public key.

### 6. Keychain rollback floor
Highest-seen config `version` stored as a Keychain item with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`
(therefore absent from backups, unaffected by container tampering). Refuse any document below the floor.
**A fresh install has no floor, and that is correct** – do not invent one.
Keychain is unavailable in a plain `swift test` process on macOS without an entitlement/keychain access;
put it behind a protocol with an in-memory test double, and keep the real implementation thin enough that
its absence from unit tests is honest rather than hidden.

### 7. Document expiry
`issuedAt` / `notAfter` are in the document (both required by the schema). An expired cached document is
discarded in favour of bundled defaults – so an attacker cannot pin a device to a stale-but-validly-signed
config forever. Uses the injected clock.

### 8. `apiBaseUrl` guardrails – the dangerous one
All five from CONFIG.md §"Guardrails":
1. **HTTPS only + compiled-in host allowlist** of domain suffixes. Any other host → rejected outright,
   previous value stands. Be careful with suffix matching: `evil-tankbook.app` must NOT match a
   `tankbook.app` suffix rule. Match on label boundaries, and test that exact case.
2. **Health gate:** a newly received base URL is a *candidate*. Probe `GET /health` against it; promote to
   active only on success. A failing candidate is discarded and logged.
3. **Auto-revert:** N consecutive transport failures (default 5, across at least two app sessions –
   `consecutiveFailures` persists in the cache file, which is what makes "across sessions" meaningful)
   → revert to the **bundled default** and re-probe.
4. Signed payload (above).
5. Version monotonicity (above).

### 9. Defence in depth – enforced in the HTTP client, not only at config-apply time
- The host allowlist is checked **in the HTTP client at request time**. Two independent checkpoints, so a
  bypass of config validation still cannot reach an attacker's host.
- **`Authorization` is attached only for allowlisted hosts.** Tokens are bound to hosts, never to
  "whatever base URL is current". Structure the code so this is not merely a check but an invariant:
  the header should be *constructible* only on the allowlisted path.
- The maintenance notice is **inert plain text** – no HTML, no markup, no arbitrary URLs, never a
  credential or re-auth prompt. The server schema already rejects `<`, `>`, `&`; do not rely on that alone,
  treat the field as plain text on the client too.
- Config can never disable a security control (TLS policy, Keychain classes, signature verification, the
  allowlist itself). These live in the binary. Make sure no config key can reach them.

### 10. Transient-unsigned-baseline case (known open item – do not skip)
Backend migration `003_remote_config.up.sql` seeds config v1 with an **empty signature placeholder**, which
`ConfigBaselineSeeder` signs at server startup. There is therefore a real window where the server can serve
a document with an empty/placeholder signature. **Assert the client rejects that state** and falls back to
bundled defaults. Add this as an explicit named test. Read the migration and the seeder to get the exact
placeholder value; do not guess.

### 11. Logging (per `docs/LOGGING.md`)
Config is our data, not the user's → Safe class. Emit `config.fetch` (status, etag, durationMs),
`config.apply` (version, changed keys **by name**, source: live/cache/bundled), `config.reject` (reason),
`config.baseurl.promote` / `.revert` (with failure count). Log the version and changed key *names*,
never the document body. Use the existing logging facility in `ios/Sources/TankbookCore/Logging/` –
add new `LogEvent` conformers next to the existing ones in `LogEvents.swift`, matching their style.
Rule 12 in CLAUDE.md is absolute: never log domain values.

## Failure behaviour (extends ERRORS.md) – all silent to the user

| Situation | Behaviour |
|---|---|
| Fetch fails (offline, 5xx, timeout) | Silent. Keep cached. Retry with backoff |
| Malformed / unsigned / older than cached | Reject whole document, keep cached, log WARN |
| One unknown key in a valid document | Ignore that key, apply the rest |
| Candidate `apiBaseUrl` fails health probe | Discard candidate, keep current, log |
| Active `apiBaseUrl` fails repeatedly | Auto-revert to bundled, log WARN |
| Maintenance notice present | The one user-visible case – quiet dismissible banner, never blocking |

Fetch is background and async. **The UI never waits on it.** A cold start with no cached config uses
bundled defaults immediately. Throttle foreground checks to once per 6 hours unless a nudge or a failure
forces it.

## Tests you must write (these ARE the acceptance criteria)

From `docs/TASKS.md` P0.12 and `docs/CONFIG.md` §Tests and §"Tests for this specifically":

1. **Bootstrap:** no cache, no network → app resolves bundled base URL and is fully usable.
2. **Brick-proof (the important one):** config names an unreachable `apiBaseUrl`, simulate N failures →
   auto-reverts to bundled default and recovers.
3. **Tamper document bytes** → rejected on read → bundled defaults.
4. **Tamper signature** → same.
5. **Version below Keychain floor** (validly signed) → rejected.
6. **Delete cache, present an old validly-signed document** → rejected by the floor.
7. **Expired document** → rejected, bundled defaults used.
8. **Non-allowlisted host forced past config validation** → the HTTP client refuses the request AND
   **no `Authorization` header was ever constructed** for that host. Assert the second part directly –
   a test that only checks the request failed is vacuous here.
9. **Allowlist near-miss:** `evil-tankbook.app` / `tankbook.app.evil.com` rejected against a `tankbook.app` rule.
10. **Rollback:** document with a lower `version` than cached is ignored.
11. **Partial-unknown:** an unknown key does not prevent the rest of the document applying, and the
    unknown key survives in the cache.
12. **Sparse override:** a document containing only `tier3CloudFallback` leaves every other resolved value
    at its bundled value.
13. **Canonicalization parity:** a fixture document with awkward numbers (`0.75`, `1e3`, a large integer),
    non-ASCII text (Cyrillic maintenance notice), nested objects with keys out of lexicographic order, and
    an empty object → your Swift canonical bytes equal a checked-in expected byte string. Generate the
    expected value by running the C# canonicalizer over the same fixture, and check both the fixture and
    the expected bytes into the repo.
14. **Transient unsigned baseline** (§10 above) → rejected.
15. **304 handling:** `If-None-Match` matching → cached document retained, no re-verify failure, no reset
    of `consecutiveFailures` semantics you did not intend.
16. **Atomic write:** a truncated/partial cache file is rejected and falls back cleanly rather than crashing.
17. **Kill switch:** flipping `tier3CloudFallback` off is observable through `ConfigStore` (the capture
    pipeline does not exist yet, so assert at the config layer, not by faking a pipeline).

Vacuous assertions are the failure mode being watched for here. `#expect(true)`, asserting only that a
function did not throw, or a "tamper" test that tampers a field the code never reads – all count as not
having done the task.
