## What to build

All in `ios/Sources/TankbookCore/`. Suggested file names; use your judgement, but keep the allowlist
and the HTTP client in separate files from `ConfigStore`.

### 1. `HostAllowlist` – compiled-in, suffix-matched, HTTPS-only

The single source of truth for "may we talk to this host". Compiled in. Suffix rule over
**`tankbook.app`**.

**Suffix matching is where this class of check is usually got wrong.** A naive
`host.hasSuffix("tankbook.app")` accepts `evil-tankbook.app`. Match on **label boundaries**: a host is
allowed when it equals `tankbook.app` or ends with `.tankbook.app`. These must ALL be rejected, and
each is a required test case:

- `evil-tankbook.app` – suffix match without a label boundary
- `tankbook.app.evil.com` – our domain as a *prefix* of theirs
- `tankbook-app.com`
- `api.tankbook.app.` – trailing dot (FQDN form)
- `API.TANKBOOK.APP.EVIL.COM` – case must not rescue it
- `http://api.tankbook.app` – right host, wrong scheme. **HTTPS only.**
- a URL with an embedded userinfo authority such as
  `https://api.tankbook.app@evil.com/` – the real host is `evil.com`. Decide deliberately how you
  extract the host (`URLComponents.host` is the safe answer, not string parsing) and test this case.

And these must be accepted: `api.tankbook.app`, `tankbook.app`, `eu.api.tankbook.app`.

Case-insensitive comparison. Reject any URL with no host, and any non-HTTPS scheme regardless of host.

### 2. Config-time enforcement – candidate, health gate, promotion

Extend `ConfigStore`. A newly received `apiBaseUrl` is a **candidate**, never applied directly.

- **Reject at validation**: a document whose `apiBaseUrl` fails `HostAllowlist` is rejected and
  **the previous value stands**. Per CONFIG.md this is an `apiBaseUrl`-level rejection – the rest of
  a valid document still applies. Read CONFIG.md's failure table and follow what it says; if it is
  genuinely ambiguous between "reject the key" and "reject the document", implement **reject the key,
  keep the previous URL**, and say in your report that you made that call.
- **Health gate**: probe `GET /health` against the candidate through the injected prober (§3).
  Promote to active only on success. A candidate that fails is **discarded, the current value stands**,
  and it is logged. Do not retry forever; one probe per refresh is correct.
- Persist the promoted value in `ConfigCacheRecord.activeBaseURL`.

### 3. The transport seam – injected, no real networking required

Define narrow protocols so every behaviour below is testable with no network:

```swift
public protocol HealthProber: Sendable {
    func probe(baseURL: URL) async -> Bool
}
```

and whatever request-executing protocol your HTTP client needs. **All of your tests must run in a
plain `swift test` with no sockets.** A test that would hit the network is a defect.

### 4. `TankbookHTTPClient` – the second, independent checkpoint

This is the most important object in the slice.

- **Enforce the allowlist at request time**, on every request, independently of config validation.
  `docs/SECURITY.md`: "Two independent checkpoints, so a bypass of config validation still cannot
  reach an attacker's host." A request to a non-allowlisted host is refused before any I/O.
- **`Authorization` is attached only for allowlisted hosts.** Structure the code so the header is
  **never constructed** for a non-allowlisted host – not built-then-dropped, not built-then-refused.
  The test asserts on construction, not just on the outgoing request.
- **Redirects re-check.** A 3xx to a non-allowlisted host must not carry the token. The natural
  implementation is a redirect handler that re-runs the same allowlist check and strips `Authorization`
  on any host change. Test it.
- The token comes from an injected provider; do not read the Keychain directly here.

### 5. Auto-revert on sustained failure

- Count **consecutive transport failures** against the active URL in
  `ConfigCacheRecord.consecutiveFailures`. Persisted, so the count **survives across app sessions** –
  CONFIG.md says "default 5, across at least two app sessions", and persistence is what makes that
  true. Make N injectable with a default of 5.
- On reaching N: **revert to the bundled default**, reset the counter, log at WARN, and re-probe.
- **Any success resets the counter to 0.** A device that fails 4 times and succeeds must not carry
  4 forward.
- Distinguish **transport** failures (cannot reach the host) from **HTTP error responses**. A 500 from
  our own server is not evidence the base URL is wrong and must not count toward the revert. Say in
  your report how you drew the line.

### 6. Logging

Add `ConfigBaseURLPromote` (`config.baseurl.promote`) and `ConfigBaseURLRevert`
(`config.baseurl.revert`, includes the failure count) next to `ConfigApply`/`ConfigReject`, matching
their style. **Rule 12: log the host and counts, never tokens, never a document body, never a
request/response payload.** A URL is our data, not the user's, so the host is loggable; an
`Authorization` value never is.

### Vacuous-assertion traps for this task – named so they do not happen

- `#expect(true)`, or asserting only that a call did not throw.
- Asserting the allowlist rejects `evil.com` while never testing `evil-tankbook.app` or
  `tankbook.app.evil.com`. **The near-misses are the test.** Rejecting an obviously unrelated domain
  proves nothing.
- Testing the allowlist *function* directly but never through the HTTP client, so checkpoint two is
  never actually exercised.
- Asserting the `Authorization` header is absent from a request object that your test constructed
  itself, rather than from the client's real path.
- A "brick-proof" test that asserts the counter incremented but never asserts recovery.
- Any test that would perform real network I/O.
