## The defect, already diagnosed

The Confirm sheet's prefill writes **raw digits** into the odometer field (`119486`) and only
groups on blur, while Home renders `123 600` from the **same** `OdometerFormat`. You can see it in
`design/screenshots/PJ.48-edit-add-receipt.png` (Edit entry, grouped, correct) against
`design/screenshots/P2.3b-confirm-fuel-multi.png` (Confirm, ungrouped, wrong).

Same class as the thin-space separator bug: **the shared formatter is correct and one screen
bypasses it.** That one shipped for the whole of P1 because a formatter test asserts a string and
the user reads pixels.

## What to build

Group the pre-filled value the way `ServiceEntry` already does -
`form.odometer = lastKnown.map(OdometerFormat.grouped)` - **keeping the type-in-raw / group-on-blur
round trip intact**. Read `ServiceEntry`'s implementation first and follow it rather than inventing
a second convention.

Note the separator is **U+00A0**, not a thin space: `DINAlternate-Bold` has no glyph for U+2009,
so a thin space renders as nothing and the odometer silently loses its separator. `OdometerFormat`
already knows this - do not hand-roll grouping.

## Named vacuous traps

- Asserting the grouped **string** only. A string test cannot see a missing glyph, which is exactly
  how the P1 bug survived. Assert the round trip too: focus strips grouping, blur restores it, and
  the parsed value is unchanged.
- Testing the formatter rather than the **screen**. The formatter is already right; the bug is that
  this screen bypasses it. The L4 assertion the row asks for is that Confirm and Home render the
  same figure identically - that is what catches a screen going its own way.
- Grouping on every keystroke. Grouped digits belong in display, never in a field being typed into.
