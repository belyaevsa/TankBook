## The defect

Found by opening PJ.11's RU screenshots: «уже зафиксирован пробег **119486** км» sitting beside a
field that renders `121 727 км`. The same screen groups one number and not the other.

`"%@ already recorded %d km."` is composed with a **raw `%d`** at three sites:

```
ManualFillUpFormState.swift:257
ServiceEntryFormState.swift:184
ImportReviewRowFields.swift:53
```

and each carries a **comment claiming "119 486 km"** - so the documented intent and the code have
disagreed all along. Verify all three yourself; briefs here have carried wrong lists six times.

This is exactly the class P1.13 fixed one layer up: **the shared `OdometerFormat` is correct and a
call site bypasses it.** P1.13's own L4 assertion could not catch this because it compares *fields*,
not the text inside a message.

## What to build

Format the number with `OdometerFormat.grouped` and pass it as `%@`, in **EN and RU**.

Note this changes the catalogue **key** (`%d` → `%@`), so it is a new key with new EN and RU values,
and the old one should go. Two things to respect:

- The separator is **U+00A0**, not a thin space: `DINAlternate-Bold` has no glyph for U+2009, which
  is how the odometer shipped unseparated for the whole of P1. `OdometerFormat` already knows this -
  do not hand-roll grouping.
- **The catalogue now has a collision guard**: no two keys may normalise to the same template
  (every specifier collapses to `%@`). `"%@ already recorded %d km."` and
  `"%@ already recorded %@ km."` **collide**, so the old key must be removed, not left beside the
  new one. If both exist the guard fails - that is the guard doing its job, not a problem to route
  around.
- RU: read `docs/LOCALIZATION.md` first. The existing RU is «"%@" уже зафиксирован пробег %d км.» -
  check that the replacement still reads correctly with a grouped number in the slot, and that no
  governing preposition sits before a runtime slot.
