## What to build

All under `ios/App/Sources/Capture/`.

### 1. `CaptureView` – the screen

Replace `ModalDestinationView`'s placeholder body for `.capture`. Layout per the artboard:

- **Camera preview** filling the screen behind everything. Use `AVCaptureVideoPreviewLayer`
  via a `UIViewRepresentable`. It must be **iOS-only** and must not crash in the simulator or
  under test, where no camera device exists – fall back to a neutral `Theme.Palette` surface.
- **Detection frame**: a rounded rect over the detected surface with the extracted lines beside
  it, as drawn in the artboard. **This is presentation only in this task** – drive it from an
  injected `CaptureDetection?` value, defaulting to nil (no frame). Do not run Vision.
- **Caption**, mode row and bottom actions per the artboard.

### 2. The mode row

`Fill-up · auto`, `Charge`, `Service`, `Expense`. Selection is local state; `Fill-up` is the
default and carries the `· auto` suffix meaning "surface auto-detected".

**`· auto` is a composed string. Do not concatenate it.** Give each language a full phrase in
the String Catalog. The P1.4 RU pass proved this: `"%@ spend"` translated word-for-word became
`"АВГУСТ РАСХОДЫ"`, word-order nonsense.

### 3. Camera permission and the F8 fallback

Check `AVCaptureDevice.authorizationStatus(for: .video)`; request on first appearance.

**Denied** → per `docs/ERRORS.md`, Capture opens **the manual form** with a top card reading
exactly:

```
Scanning needs the camera – enable in Settings.
```

with **three** next steps: **Settings** (deep link via
`UIApplication.openSettingsURLString`), **Type it** (the full manual path), and **Photos**
(library). Hard rule 7: every error names its next step, and the screen must survive the error
being ignored – a denied permission must never be a dead end.

Put the permission check behind an injected protocol so tests can drive all of
`.authorized / .denied / .notDetermined` without touching the real system:

```swift
protocol CameraAuthorizing: Sendable {
    func status() -> CaptureCameraStatus
    func request() async -> CaptureCameraStatus
}
```

### 4. Wiring

- `Photos` opens `PHPickerViewController` – present it and accept the image. **Do nothing with
  the image** beyond holding it; parsing is P2.2.
- `Type it` routes to the existing manual form (the `-openManualForm` / ConfirmManual path
  already in the app). This path must work even when the camera is denied.
- **Info.plist**: `project.yml` uses `GENERATE_INFOPLIST_FILE: YES`, so add
  `NSCameraUsageDescription` and `NSPhotoLibraryUsageDescription` via `INFOPLIST_KEY_*` build
  settings on the `Tankbook` target in `project.yml`, then run `xcodegen generate`. Copy that
  reads as a reason, not a formality, and localised in the String Catalog.

## Tests – these ARE the acceptance criteria

**Unit tests** in `ios/Tests/TankbookCoreTests/` only if you put logic in `TankbookCore`;
otherwise put screen logic in the app target and test it through the UI suite. Current counts:
**`swift test` 349**, **UI tests 59**. Both must rise.

**UI tests** in `ios/App/UITests/` (XCUITest), matching the existing suites' style:

1. **F8 denied-permission flow**: launch with the injected status forced to `denied` (add a
   DEBUG launch argument, e.g. `-cameraStatus denied`, alongside the existing hooks) → the
   manual form is shown with the permission card, and **all three** next steps are present and
   tappable. Assert the card's text, not just its existence.
2. **"Type it" path** reaches the manual form from Capture with permission **granted**.
3. **The mode row** renders all four modes, `Fill-up` is selected by default, and tapping
   another mode changes the selection.
4. **X closes the cover** and returns to the opener – `captureCloseButton` must still work.
5. **Denied permission is not a dead end**: from the F8 state the user can still reach a
   savable manual form (hard rule 7).

Use the `scrollTo` helper's frame-clearing form if you need to scroll – the older
`isHittable` version stops on an element's **centre**, so it can stop while the bottom edge is
still under the keyboard. Two AddVehicle tests are load-sensitive for exactly this reason; do
not add a third.

### Vacuous-assertion traps for this task

- `#expect(true)`, or asserting only that a view exists without asserting its text.
- Asserting the permission card appears without asserting **all three** next steps.
- A test that passes because the camera is unavailable in the simulator and every path
  silently falls into the same fallback – force the status explicitly instead.
- Testing the mode row by accessibility identifier only, so a mode whose **label** is wrong
  still passes.
