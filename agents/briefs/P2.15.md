## The defect, traced end to end – do not re-diagnose it

Reported by the product owner, 2026-08-30: numeric fields let you type letters.

All 16 numeric fields set only `keyboardType(.numberPad)` / `.decimalPad`. **That is a hint, not a
constraint** – a hardware keyboard (the simulator, an iPad, any Bluetooth keyboard), **paste**, and
dictation all bypass it. This is reachable on a shipping device; it is not a simulator artefact.
There is **no input filtering anywhere in the app** (verified by grep).

What then happens, on the odometer:

1. `ManualFillUpFormState.odometerValue` is `Int(OdometerFormat.ungrouped(trimmed))` -> **nil** for
   `12a34`.
2. Save is gated on **total + litres only**; the odometer never gates it.
3. `ManualFillUpView.swift:653` writes `odometer: form.odometerValue` – i.e. **nil**.

**The user sees their text in the field, taps Save, and the odometer is gone.** No error, no
warning. That is hard rule 8 (*nothing lost silently*) and hard rule 7 (*every error names its next
step*). And because stats are derived (hard rule 2), one odometer-less fill degrades the consumption
figure for the entries around it, not only its own row.

The same shape exists at `AddVehicleView.swift:183` (`initialOdometer`) and
`VehicleDetailFormState.swift:99`, and the money and litres fields parse the same way.

## What to build

**Filter at the binding** – the product owner's decision. Garbage never enters the field, so there
is nothing to discard and nothing to warn about.

1. Digits only for integer fields (`.numberPad`).
2. Digits plus **one** separator for decimal fields (`.decimalPad`), and the separator must be the
   **locale's**: RU types a comma. The corpus is blunt about this – the decimal separator belongs to
   the device, not the country – so accept both `.` and `,` as input and normalise, rather than
   hard-coding one. A second separator is rejected, not appended.
3. Applied at **all 16 sites**. Fixing only the odometer is the exact shape that has cost this
   project twice: the contrast guard was written for the defect in front of it and left a worse case
   untouched, **both times it was written**. The class here is "every field that parses text into a
   number", not "the field the owner happened to report".
4. Paste of a mixed string keeps the usable digits rather than clearing the field – a user pasting
   `119 486 km` should not be punished with an empty field. Say what you chose and why.

## Where the logic goes, and why it is not optional

**The sanitizer is a pure function in `TankbookCore`**, unit-tested at L1; the app layer only
applies it. This repo has a scar exactly here: `AppTabBar`'s padding arithmetic lived in the app
target, which the package tests cannot import, so a double-counted inset was "verified by looking at
one device" and survived two whole phases. A string-in/string-out sanitizer is the easiest possible
thing to test, and there is no reason for it to live where tests cannot reach it.

## Named vacuous traps for this task

- **A test that types only valid digits cannot see this bug.** Every new test must feed something a
  `numberPad` would not produce: `12a34`, `1..2`, `1,2,3`, `abc`, an empty paste, `119 486 km`.
- Testing the sanitizer only, and never that a **field** uses it – 16 call sites are the actual
  deliverable, and a perfect untested-at-the-call-site helper leaves the bug shipping.
- Asserting a field "rejects input" by checking the model is nil – that is the current behaviour and
  the defect.
- Hard-coding `.` as the decimal separator and calling the RU case done.
