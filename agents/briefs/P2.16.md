- **`Test Suite 'CaptureUITests' passed`** was printed anyway. Same for the other two.

A green result that measured nothing is the failure mode this project fears most – the sibling of
"a `--filter` matching nothing prints *Test run with 0 tests ... passed*". It makes every green run
un-trustworthy until explained.

**Diagnose it before fixing anything.** One candidate, not a conclusion: `docs/TESTING.md` and the
briefs warn *never drive the simulator while `xcodebuild test` is running – they fight over the
device*. Another agent's screenshot capture (`simctl`) was writing files at **17:45-17:46**, and
this run started about **17:47**, so they may have overlapped. Test that hypothesis rather than
assuming it: re-run `CaptureUITests` alone on an idle machine and see whether it executes its full
count; look for runner restarts, app crashes or "Lost connection" in the log.

**Deliverable, whatever the cause: an under-run must FAIL, not pass.** The suite's own count is the
only thing that can catch this, so produce a gate that compares the **observed executed count**
against the expected number of `func test` declarations and exits non-zero on a shortfall. A script
under `scripts/` that a human or CI can run after `xcodebuild` is enough. Record the rule in
`docs/TESTING.md`. **The gate must be mutation-checked**: feed it a log with a deliberately reduced
count and confirm it exits non-zero; feed it a full one and confirm zero.

- "Fixing" the budget test with `sleep`/`Thread.sleep` or by raising the 3 s product number.
- `XCTSkip`, a deleted assertion, or an assertion that cannot fail.
- Declaring part 1 "not reproducible" and stopping. If it does not reproduce, the gate in part 1 is
