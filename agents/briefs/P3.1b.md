## The rule this task exists to honour

**Hard rule 15 – two doors, always, and a capture is a head start, not an answer.** Whatever the
scan produces is a **default input the user edits** (hard rule 13), so a poor split degrades to
"rename two rows", never to "start over". `docs/JOURNEYS.md` J7 is normative and blunt about it:

> "OCR can't split the invoice → the *same screen* holds one uncategorized item with the full
> total; the user renames/splits by hand or leaves it as 'Annual service · 148 €' – **a lump sum
> with the bill attached is a perfectly good record (never force itemization)**."

Two consequences you must design for rather than treat as edge cases:

1. **Invoices are far messier than fuel receipts**, and the corpus already shows the fuel parser
   at 41.6%. Expect the split to fail often. **A failed split is the lump-sum path, which P3.1a
   already built and tested** - it is a normal outcome, not an error state, and it shows no error.
2. **There is no on-device LLM.** Tier 2 was **cut on 2026-08-25** (`docs/VISION.md` -> "Why tier
   2 was cut": Foundation Models has no Russian). J7's line-splitting is **deterministic rules
   over OCR text**, full stop. Do not write an `#available(iOS 26)` normalization hook, and do
   not call any model.

## What to build

1. **Capture -> ServiceEntry.** `Capture`'s Service mode opens the document camera and lands in
   ServiceEntry with a prefill. `SCREENMAP.md` already draws this edge; make it true.
2. **Multi-page.** Pages are captured into one `ServiceRecord`'s attachments, with the artboard's
   page strip and "+ add page". Removing a page is possible and does not orphan its file.
3. **Attachment persistence.** Each page is stored as an `Attachment` with `ocrText` retained -
   `SCHEMA.md` keeps it deliberately, so a future parser upgrade can re-parse without the user
   re-scanning. `extractedTimestamp` is set when the invoice's printed date is readable, and it
   pre-fills the date row's provenance caption ("· invoice") that P3.1a left room for.
4. **Line splitting, deterministic.** Over the OCR lines of all pages: candidate rows of
   `title` + amount, a total line, and a vendor from the header. Category is guessed from a small
   vocabulary and **is always a suggestion the user overrides** (hard rule 13).
   **The load-bearing rule, and the one to test hardest: the sum of split items must equal the
   invoice total within the CHECK 3 tolerance `max(0.02, total × 0.005)`, and when it does not,
   the split is discarded entirely in favour of the lump sum.** A partial split that silently
   loses a line is worse than no split - it produces a wrong number that looks right, which is
   exactly the failure mode the fuel corpus documented (`a × b == b × a` passing a green
   cross-check on a swapped pair).
5. **Provenance.** `ExtractionMeta.pipeline` records what produced the split (e.g.
   `"vision+rules invoice v1"`), and `.lineItem(Int)` field extractions carry confidence so
   P3.1a's dimming applies to scanned rows.
6. **Strings** through the String Catalog, EN **and** RU. **Read the rule at the top of
   `ios/App/Sources/Localization/L10n.swift` first** - `Text(_: String)` does not localise, so any
   expression where runtime data and copy share one expression renders its English key, and the
   gate cannot see it. Four bugs have shipped that way. "Page 1 of 3" is exactly that shape:
   a full localised phrase per language, never concatenation.

1. **The sum invariant, both directions** (L1): a fixture whose items sum to the total splits; a
   fixture where they do **not** falls back to the single lump-sum item with the full total. Test

5. **The prefill is editable everywhere** (L4, hard rule 13): every scanned row - title, category,

### Vacuous-assertion traps for this task

- `#expect(true)`, or asserting only that a call did not throw.
- A split test whose fixture has one line item - it cannot distinguish splitting from lump-sum.
- Asserting the sum invariant only on the passing side. The bug is a split that loses a line, and
  a one-sided test stays green straight through it.
- Testing the parser on text you wrote to match your parser. Use OCR text captured from a real
  invoice image, or at minimum text transcribed verbatim from one, and say in your report which
  it was.
- A "page removed" test that checks the array count without checking the file.
