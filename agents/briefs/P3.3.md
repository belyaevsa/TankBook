## The rule this task exists for

`docs/SCHEMA.md`, verbatim:

> ```
> TireSet {                       // v1.x - seasonal sets with their own mileage
>   id, createdAt, updatedAt, deletedAt
>   vehicleId: UUID
>   name: String                  // "Winter Nokian", "Summer Michelin"
>   purchaseExpenseId: UUID?      // the Expense(.parts) that bought them
>   // km on this set is DERIVED: sum of odometer spans between ServiceRecords that mounted/unmounted it
>   // (tireSetId marks mounting; the next tire-swap record ends the span). Never stored - same rule as segments.
> ```

**Derived, never stored** is hard rule 2 (`CLAUDE.md`): stats recompute, they are not cached. A
tire set's mileage is the sum of odometer spans between the record that mounted it and the record
that mounted something else.

The second rule, from `docs/TASKS.md`'s own check for this task: **"– when unknowable."** A span
whose bounding odometer is missing does not contribute a guess. An open span (the set is on the
car right now) runs to the latest known odometer, and a set that has never been mounted shows a
dash, not a zero - zero is a claim, and it is false.

## What to build

1. **Tire sets on a vehicle**: create, rename, archive. A set belongs to one vehicle.
2. **Mounting**: a ServiceRecord with `tireSetId` set mounts that set; the next record mounting a
   *different* set ends the previous span. The ServiceEntry screen's **Tires** mode is where this
   is chosen - and remember the odometer rule P3.1a built: **mounting a tire set makes the
   odometer required**, because the span anchors on it (that logic already exists in
   `ServiceEntryDraft.requiresOdometer`; do not duplicate it).
3. **Derived mileage**, in `TankbookCore` as a pure function over records - the shape
   `ConsumptionEngine` uses:
   - closed spans sum;
   - the currently-mounted set's span runs to the latest known odometer;
   - a span with a missing bounding odometer is **excluded, not estimated**;
   - a set never mounted, or with no usable span, yields **nil** -> the UI renders "–".
4. **Display**: each set shows its name and its derived mileage ("Winter Nokian · 18 400 km"),
   with "–" where unknowable. Use `OdometerFormat.grouped` - it is the shared formatter and its
   separator is U+00A0 for a reason (DIN has no thin-space glyph; see `OdometerFormat`).
5. **Strings** through the String Catalog, EN **and** RU. **Read the rule at the top of
   `ios/App/Sources/Localization/L10n.swift` first** - `Text(_: String)` does not localise, so an
   expression mixing runtime data and copy renders its English key while the gate stays green.
   Five bugs have shipped that way. "Winter Nokian · 18 400 km" is exactly that shape.

1. **Span math across mount/unmount** (L1): three swaps across two sets produce the right totals

2. **The open span** (L1): the set mounted now runs to the latest known odometer, and that total
   grows when a later fill-up raises the odometer.
3. **"– when unknowable"** (L1) - the invariant of this task, tested in **both** directions: a
   span missing a bounding odometer is excluded and the result is nil; a set with a usable span
   still returns a number. A rule that always returned nil would pass a one-sided test while
   making the feature useless.
4. **Zero is never shown for unknown** (L1/L4): a never-mounted set renders "–", not "0 km".
5. **Derived, never stored** (L1): no `TireSet` field caches the mileage; recomputing after
   editing a record's odometer yields the new number with no explicit invalidation.
6. **L4**: the tire-set list renders with mileage and with "–"; mounting from the Tires mode saves
   and requires the odometer (P3.1a's rule, exercised through this path).

### Vacuous-assertion traps for this task

- `#expect(true)`, or asserting only that a call did not throw.
- Testing the span with **two** records - it cannot distinguish "sum of spans" from "latest minus
  first", which is the bug that appears the moment a set is remounted.
- Asserting nil for an unknowable span **without** asserting a number for a knowable one.
- Building expectations by calling the same function the code uses. Write the expected kilometres
  as **literals** in the test.
- Storing the derived value anywhere to make a test easier.
