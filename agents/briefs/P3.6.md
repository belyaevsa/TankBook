## The rules this task exists to honour

`docs/NOTIFICATIONS.md` is the authority, quoted verbatim where it is normative:

- **Date reminder** -> "Morning of the due-window start (**09:00 local**), one line: *Insurance
  renews in 12 days.*"
- **Odometer reminder** -> "**Local, armed at write time** … Scheduled the evening after the save
  that crossed the threshold: *Oil change within 500 km.*"
- **Overdue follow-up** -> "**Exactly one, 7 days after due** … **Never a nag loop.**"
- **Quiet by scheduling, not by feature**: "everything user-visible fires at humane fixed times
  (09:00/10:00 local) - there is nothing time-critical in a fuel log, so **nothing ever needs to
  buzz at night**."
- **Cancellation**: "**any change that resolves a notification's reason cancels it everywhere** -
  completing/rescheduling a reminder syncs, and each device cancels its pending local notification
  for it on merge."
- **Permission** is requested "**at the first moment it's needed** (creating the first reminder),
  never at onboarding". Denied -> the one-time card from `ERRORS.md`, deep link, **no nag loop**.

The odometer case is the subtle one and the reason this task is not "schedule a date": an odometer
threshold is crossed by a **fill-up being saved**, not by time passing. Arming happens at write
time, and the notification lands the following evening.

## The testability constraint - read before designing

`UNUserNotificationCenter` cannot be asserted against in a unit test, and a UI test cannot see a
pending notification. So the **decisions must be a pure value type in `TankbookCore`** and the
`UNUserNotificationCenter` call must be a thin, injected adapter - the same split as
`ServiceEntryDraft`, `PumpPhotoGate`, `TireMileage` and `TabBarMetrics`.

Concretely: something like `ReminderNotificationPlan` that, given reminders, "now", and the
current odometer, returns **what should be scheduled and what should be cancelled** - dates,
identifiers, bodies. The tests assert that plan. The adapter that hands it to
`UNUserNotificationCenter` stays dumb enough to read in one screen, and takes a protocol so a test
double can record calls.

**A design that puts the scheduling logic inside a `UNUserNotificationCenter` call site is not
acceptable here**, because it cannot be tested and the phase gate requires it to be.

## What to build

1. **The plan type** in `TankbookCore`: date reminders at **09:00 local** on the due-window start;
   odometer reminders **armed at write time**, scheduled for the **evening after** the crossing
   save; **exactly one** overdue follow-up at **due + 7 days**; nothing scheduled outside humane
   hours, ever.
2. **Cancellation**: completing, rescheduling, dismissing or deleting a reminder cancels its
   pending notification. A rescheduled reminder that fired `.attention` can arm again (P3.4's
   rule).
3. **The adapter**: an injected protocol with a real `UNUserNotificationCenter` implementation and
   a recording double for tests. Request permission **at the first reminder creation**, never at
   launch; denied is a one-time card with `ERRORS.md`'s copy and no repeat.
4. **Wire the arming** into the fill-up save path so an odometer threshold crossed by a save arms
   the notification.
5. **Strings** through the String Catalog, EN **and** RU. **Read the rule at the top of
   `ios/App/Sources/Localization/L10n.swift` first** - `Text(_: String)` does not localise, so an
   expression mixing runtime data and copy renders its English key while the gate stays green. Six
   bugs have shipped that way. "Oil change within 500 km" and "Insurance renews in 12 days" are
   exactly that shape: a full localised phrase per language, never concatenation, with Russian
   plural rules (1 день / 2 дня / 5 дней; 1 км / 2 км).

4. **Resolution cancels** (L1): completing, rescheduling, dismissing and deleting each produce a
   cancellation for that reminder's identifier - four cases, not one.
5. **Rescheduling re-arms** (L1): a fired `.attention` that is rescheduled can notify again.
6. **Permission** (L1/L4): requested at first reminder creation, not at launch; denied renders the
   `ERRORS.md` card once and never again.
7. **L4**: the permission-denied card renders; a reminder created with notifications denied still
   saves and still shows in the list (nothing is ever notification-gated - hard rule 1).

### Vacuous-assertion traps for this task

- `#expect(true)`, or asserting only that the adapter was called.
- Testing the overdue follow-up **once**. The rule is "exactly one, never a nag loop" - a single
  call cannot distinguish one from many. Advance time and assert the count stays 1.
- Asserting humane hours by formatting a string. Assert `DateComponents.hour`.
- A cancellation test that checks only completion. There are four resolving transitions.
- Mocking the plan and asserting the mock. The plan **is** the logic; assert its output.
