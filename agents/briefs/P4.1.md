## The contract, verbatim from `docs/API.md` (the authority)

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /auth/session` | identity token | Exchange a Sign in with Apple / Google ID token for a session. Body: `{ provider: "apple"\|"google", idToken, device: { name, platform } }` |
| `POST /auth/refresh` | refresh token | `{ refreshToken }` -> new token pair. **Refresh tokens rotate; reuse of a rotated token revokes the chain (theft signal).** |
| `DELETE /auth/session` | bearer | Sign out this device (revokes its refresh chain; **local data stays local**). |

`docs/SECURITY.md` adds what must hold on the server side:

- The **access token is a JWT, ~1 hour**; the refresh token rotates on every use.
- Verification is **server-side against fetched JWKS with caching** - Apple/Google public keys are
  not secrets, but a token's signature must be checked, never trusted.
- **Never log a token, an `idToken`, or an email** (`docs/LOGGING.md` hard rule 12: ids, counts,
  codes and field *names* are loggable; values are not).
- **`sign-in IS registration`** (`CLAUDE.md`, decided): a first sign-in creates the account. There
  is no separate registration endpoint and no account linking in v1.

## What to build

1. **A new migration** adding refresh-token storage. It must support **rotation** and **reuse
   detection**: a rotated token that is presented again revokes the whole chain. Store a **hash**
   of the token, never the token itself - a database dump must not yield working credentials.
2. **`POST /auth/session`**: verify the provider `idToken` against cached JWKS, find-or-create the
   account by `apple_sub`/`google_sub`, register the device, return the token pair plus the
   `deviceId`. **Concurrent first sign-ins for the same subject must create exactly one account** -
   the unique constraints exist for that; make the code agree with them under real concurrency.
3. **`POST /auth/refresh`**: rotate. Issue a new pair, invalidate the presented token, and on
   **reuse of an already-rotated token revoke the entire chain** and reject.
4. **`DELETE /auth/session`**: revoke this device's chain. Local data is untouched - this endpoint
   deletes no records.
5. **Bearer authentication** for the endpoints that will need it, as middleware or a filter other
   modules can adopt (P4.2/P4.3 will).
6. **JWKS fetching with caching** and a **test seam**: an injected verifier interface with a
   test-signer implementation, so L2 tests can mint tokens without the network. Real JWKS
   fetching stays behind the same interface.

## Tests (L2, against real Postgres via Testcontainers)

Count now: `dotnet test` **134**. It must rise.

1. **Test-signer tokens are accepted; garbage and expired ones are rejected** with the documented
   status, not a 500.
2. **Concurrent first sign-in creates exactly one account** - run the exchange in parallel for one
   subject and assert a single `accounts` row. This is the race the unique constraints are for.
3. **Refresh rotates**: the old token stops working the moment the new pair is issued.
4. **Reuse revokes the chain** - present a rotated token and assert *both* that it is rejected and
   that the chain's current token is now dead too. **A test that only asserts the rejection misses
   the revocation**, which is the security-relevant half.
5. **Sign-out revokes only that device**: a second device's tokens keep working, and **no records
   are deleted**.
6. **No token, `idToken` or email appears in any log line** (hard rule 12) - assert against the
   captured log output, the way `backend/tests/.../Logging` already does.
7. **Apple and Google subjects are distinct**: the same `sub` value from different providers is two
   accounts, not one.

### Vacuous-assertion traps for this task

- Asserting a 200 without asserting **what changed in the database**.
- Testing rotation with one refresh. Rotate twice and assert the first token is dead after the
  second rotation.
- Mocking the repository and asserting the mock. These are L2 tests against real Postgres.
- Storing refresh tokens in plaintext and testing that they compare equal - assert the column does
  **not** contain the token value.
- A concurrency test that runs sequentially. Use real parallel tasks.
