## Why this is the first P4 task, before any sync work

`Records.swift` stores every date as `timeIntervalSince1970`. Adding the **978 307 200 s** epoch
offset shifts the fractional bits out of the Double mantissa, so a record read straight back after
a write differs from what was written by **one ulp (~1.2e-7 s)** on `createdAt` / `updatedAt`.

Measured, not assumed: the drift is **idempotent** - a second round trip is stable - so nothing is
broken today. But **the whole of P4 leans on "a record read back equals the record written"**:
`updatedAt` is the LWW comparator in `docs/SYNC.md`, the S1-S8 scenarios assert exact outcomes, and
restore-from-zero must hash-equal the origin dataset. Fixing it after the sync client is written
means re-verifying every one of those.

It was found by P3.1a's round-trip test - the first in the repo to assert **whole-record** equality
rather than field-by-field, which is why it survived P0.4.

## What to build

1. **Store `timeIntervalSinceReferenceDate`, not `timeIntervalSince1970`.** `Date`'s own storage is
   `timeIntervalSinceReferenceDate`, so writing and reading that value is an exact Double round
   trip with no offset arithmetic.
2. **A migration.** This is a **column value format change**: existing rows hold epoch-1970
   seconds and must be converted (`value - 978307200`). Follow the existing migration pattern in
   `ios/Sources/TankbookCore/Persistence/Migrations.swift`; it must apply forward over a seeded
   database, and every converted value must equal the original **to the second**.
3. **Every date column**, not just the envelope: `createdAt`, `updatedAt`, `deletedAt`, entry
   `date`, `Money.rateDate`, `archivedAt`, `Attachment.extractedTimestamp`, and any other
   `timeIntervalSince1970` in `Records.swift` / `Records+Extras.swift`. Grep for it - a missed
   column is a silently half-migrated database.
4. **Delete the tolerance that hides it.** `ios/Tests/TankbookCoreTests/ServiceEntryTests.swift`
   currently normalises the two envelope timestamps before comparing and asserts a sub-millisecond
   bound, with a comment naming P4.11. That normalisation and the tolerance both go; the test
   asserts **whole-record equality** with no exceptions.

## What NOT to explore – closed questions

- **Whether to keep `Double`.** GRDB stores it natively and `Date` is a `Double` underneath; do
  not switch to ISO-8601 strings or integers. The bug is the **offset**, not the type.
- **The sync protocol.** P4.2/P4.5 own it. This task changes local persistence only.
- **The backend.** A different agent is working in `backend/` right now. Do not touch it.
- **Foundation Models / any LLM.** Tier 2 was cut on 2026-08-25 (`docs/VISION.md`).

### Vacuous-assertion traps for this task

- `#expect(true)`, or asserting only that a call did not throw.
- Comparing with `abs(a - b) < tolerance` **anywhere** in a new test. A tolerance is what hid this
  bug for the whole of P0-P3; the point of the task is that equality now holds.
- Testing the migration with a date of `0` or a whole second - the offset error only appears in the
  fractional bits, so a whole-second fixture passes either way.
- Migrating the schema but leaving the old writer in place, so new rows are written in the old
  format. Write and read must change together.
- "Fixing" a failing golden vector by editing the vector.
