## Why this task exists, and why it gates P4.10

A first probe on 2026-08-26 was decisive enough to change what the LLM gateway is for:

- On **pump displays**, where the rules parser scores **1/46 fields**, the vision model read
  **9 of 12** fields exactly - including `pump-004`, the fixture where Apple's Vision returns a
  **wrong digit at confidence 1.00**.
- Its two failures are the corpus's own documented traps, and **both pass an arithmetic
  cross-check**:
  - `pump-005` lost a decimal separator (`5.256` / `462.08` - a clean factor-of-ten shift);
  - `receipt-035` **swapped** volume and price (`70.44 X 39.000` read as 70.44 L).

So the model is strongest exactly where the parser is blind, **and its failure modes are silent**.
`CLAUDE.md` hard rule 13 is what makes that decisive: **a confident wrong value is worse than a
`nil`**. The parser's `nil` costs the user two taps; a swap costs them a silently wrong
consumption figure for the life of the vehicle.

**P4.10 (the gateway server) must not be designed until this is measured.** That is why this task
comes first.

## How to call the model

Sequentially, one image at a time:

```
opencode run --auto -m deepseek/deepseek-v4-flash-vision-exp -f <image-path> "<your prompt>"
```

**Fully qualify the provider** (`deepseek/...`). A bare model name resolves to a different
provider that has returned an instant `UnknownError` on every model it carries; the tell is a
~166-byte response that is all error JSON.

**Run them one at a time, never in parallel.** Two `opencode` processes starting in the same
instant kill one another on opencode's local store ("database is locked"), and you would silently
lose images from the sample. Expect **4-7 s per image**; the corpus is ~62 images, so budget
10-20 minutes for a full sweep and let it run.

If a call fails, **record it as a failure for that image and continue**. A sweep that aborts
halfway measures nothing, and a silently skipped image inflates the score.

## Tests

Count now: `swift test` **593**. It must rise, but only with tests that do not require the network.

**Split the network from the scoring.** The sweep hits a paid remote model; the *scoring* must run
offline against the committed result file, so the suite stays deterministic and CI never calls the
model. Tests assert the scorer and the two failure-mode cases against **recorded** results.

1. The scorer gives **identical numbers for the rules arm** as `AccuracyRatchetTests` does - proof
   the two arms really share a scorer.
2. `receipt-035`'s recorded LLM output **is** the swap, and a `liters x unitPrice == total`
   cross-check **passes** on it anyway.
3. `pump-005`'s recorded LLM output is the factor-of-ten shift, and the cross-check **passes** on
   it anyway.
4. An **empty** `expected.csv` field is skipped, not scored as a miss - on both arms.
5. A recorded per-image **error** counts as a miss, never as a skip. Silently dropping failures is
   how a sweep flatters itself.

### Vacuous-assertion traps for this task

- Scoring the two arms with two different comparisons or tolerances.
- Reporting only aggregate percentages. The whole point is that **two silent failures matter more
  than a higher average**.
- A test that calls the model. It will be slow, cost money, and be flaky in CI.
- Treating a failed call as a skip, which raises the score by losing data.
- Writing LLM numbers into `high-water.json`.
- Asserting the cross-check "catches" the swap. It does not - `a x b == b x a`. If your test says
  otherwise, the test is wrong.
