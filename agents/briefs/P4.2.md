## The contract, verbatim from `docs/API.md` (the authority)

```
GET /sync/pull?since=<SCN>&limit=500        // since=0 -> full dataset
-> 200 { records: [ { id, entityType, schemaVersion, scn, payload, clientUpdatedAt, deleted } ],
         nextSince: <SCN>, more: bool,
         schemaPolicy: { minSupported: int, current: int } }
-> 410 device revoked / account deleted -> client re-onboards or detaches
```
```
POST /sync/push   { changes: [ { id, entityType, schemaVersion, baseScn,   // 0 for new records
                                 payload, clientUpdatedAt, deleted } ] }   // <= 200 changes/batch
-> 200 { results: [ { id, status: "accepted", newScn }
                  | { id, status: "conflict", current: <record> }
                  | { id, status: "rejected", error: <code>, pointer: <json-pointer> } ] }
-> 426 upgrade_required   // whole batch; PULL still works - never lock a user out of their data
```

**Fetching the latest data IS pulling from 0** - fresh install, restore and incremental catch-up
are the same call. There is no separate restore endpoint.

## The rules that make this task hard

- **Hard rule 9: the server validates payload STRUCTURE, never domain MEANING.** Envelope, size,
  and the registered JSON Schema are enforced. No endpoint reads what a field means; there are no
  domain queries, no search, no stats. A `rejected` result names a **code** and a **JSON pointer**,
  never an opinion about the value.
- **SCN is strictly monotonic per account**, allocated on write from `account_seq`. Two devices
  pushing concurrently must never receive the same SCN, and a pull cursor must never skip a record.
  This is the one place a race corrupts the user's history silently.
- **Both endpoints are idempotent.** A replayed batch produces the same outcome, not duplicates.
- **`conflict` returns the server's current record** so the client can merge and re-push
  (`SYNC.md` S1/S6). The server does not merge.

## Tests (L2, against real Postgres via Testcontainers)

Count now: `dotnet test` **144**. It must rise.

1. **Ordering and pagination under concurrent writes**: with writers pushing while a reader pages
   through, the reader sees every record exactly once and never skips one. Assert the union of
   pages equals the full set - **the assertion that catches a cursor that advances past an
   in-flight commit**.
2. **Idempotent replay**: pushing the same batch twice yields the same results and leaves one row
   per id, not two.
3. **Per-item conflict**: a change whose `baseScn` is behind the server returns `conflict` **with
   the server's current record**, and the other items in the same batch still succeed. Partial
   success is the contract; an all-or-nothing batch is wrong.
4. **`rejected` carries a code and a pointer**, and the batch's other items are unaffected.
5. **410 on a revoked device** - and assert that `PULL` for a *live* device on the same account
   still works, so revocation is per device.
6. **426 blocks push but NOT pull** - the documented "never lock a user out of their own data".
7. **SCN is strictly monotonic per account under concurrency**: N parallel pushes produce N
   distinct, increasing SCNs. Run it genuinely in parallel.
8. **No payload, amount or token reaches a log line** (hard rule 12) - assert against captured log
   output, as `backend/tests/.../Logging` already does, and assert the sync event lines *are*
   present so the capture is proven non-empty.

### Vacuous-assertion traps for this task

- A "concurrency" test that runs sequentially. Use real parallel tasks and assert the invariant,
  not the happy path.
- Asserting a 200 without asserting **what the database now contains**.
- Testing conflict with a single-item batch - it cannot show that the other items still succeed.
- Asserting `nextSince` advanced without asserting **no record was skipped**. That is the failure
  that loses a user's data silently.
- Re-validating payloads with new code instead of `PayloadValidator`.
