## The rule this task exists to honour

**Hard rule 1: no feature may require the network, and no screen is ever sync-gated.** Sign-in is
optional, always. The app must stay fully usable with no account, and a failed or declined sign-in
returns the user to a working app, never to a wall.

**`docs/JOURNEYS.md` J11a is the authority**, and its trap is the point of this task, quoted:

> **The wrong-provider trap:** the user signed in with Google on Android but taps Apple on the new
> iPhone -> two identities, two accounts, and the "restore" finds an empty account. v1 ships **no
> account linking**; two mitigations. *Proactive:* the Sign in screen carries a warn-amber notice
> at the decision moment - "Pick one and keep it. Apple and Google create separate accounts - use
> the same one on every device." *Reactive:* honest detection - if the signed-in account is empty
> *and* the user came through "Already use Tankbook?", say "Nothing is stored under this Apple ID.
> Last time, did you sign in with Google?" with a one-tap provider switch - **never show an empty
> garage as if their data were gone.** (Same guard in reverse when a local log exists: J11a never
> overwrites local data - it uploads it.)

## What already exists – build on it, do not redesign

- **The backend auth endpoints are merged and tested** (P4.1): `POST /auth/session` takes
  `{ provider, idToken, device: { name, platform } }` and returns a token pair plus `deviceId`;
  `POST /auth/refresh` rotates; `DELETE /auth/session` signs out this device. `docs/API.md` is the
  contract.
- `ios/App/Sources/Persistence/AppStore.swift` and the repository - local data, which sign-in
  **never** replaces.
- `ios/Sources/TankbookCore/Config/` and `TankbookHTTPClient` - the HTTP client, and the **host
  allowlist** that decides when `Authorization` may be attached at all.
- `design/screens/SignIn.dc.html` and `design/screens/Restoring.dc.html` - **the pixel
  authorities**.
- `ios/App/Sources/Sheets/ConfirmableFormScreen.swift` - the shared shell for a form with a
  primary action, if you need one.
- `docs/SECURITY.md` -> the storage table. **This is normative and not negotiable:**

| Item | Where | Accessibility |
|---|---|---|
| Access token (JWT, ~1h) | Keychain, `kSecClassGenericPassword` | `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` |
| Refresh token (rotating) | Keychain, separate item | same |
| `deviceId` | Keychain | same |

**`ThisDeviceOnly` on every item** - it keeps tokens out of iCloud Keychain and out of backups, and
it is what makes per-device revocation meaningful. A synced session would silently defeat it.

**The token is bound to the host, not to the session**: `Authorization` is attached only when the
request host is on the compiled-in allowlist, enforced in the HTTP client. Never attach credentials
to "whatever base URL is currently configured".

## What NOT to explore – closed questions

- **Account linking.** Not in v1. Two providers are two accounts; the mitigation is the notice and
  the honest detection, not linking.
- **The sync client itself** (dirty queue, merge loop) - that is **P4.5**.
- **Blobs** (P4.3/P4.6), **Settings account states** (P4.9).
- **Real Apple/Google SDK sign-in flows** beyond what `AuthenticationServices` gives you: the
  server verifies the token, so the client's job is to obtain it and hand it over. Provide an
  injected protocol with a test double so the flows are testable without a real Apple ID.
- **Foundation Models / any LLM.** Tier 2 was cut on 2026-08-25.

### Vacuous-assertion traps for this task

- Asserting the Keychain round trip without asserting the **accessibility class**.
- Testing J11a with a **non-empty** account - the trap only exists when the account is empty.
- A "local data preserved" test with an empty local database.
- Mocking the HTTP client and asserting the mock, rather than asserting the header the real client
  would attach.
- `#expect(true)`, or asserting only that a call did not throw.
