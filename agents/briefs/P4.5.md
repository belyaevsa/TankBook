## The contract, verbatim from `docs/API.md` (the authority for the wire)

```
GET /sync/pull?since=<SCN>&limit=500        // since=0 -> full dataset
-> 200 { records: [ { id, entityType, schemaVersion, scn, payload, clientUpdatedAt, deleted } ],
         nextSince: <SCN>, more: bool,
         schemaPolicy: { minSupported: int, current: int } }
-> 410 device revoked / account deleted -> client re-onboards or detaches
```

> Strictly SCN-ordered, paginated; the client persists `nextSince` per device **only after
> applying the page**.

```
POST /sync/push
{ changes: [ { id, entityType, schemaVersion, baseScn,   // baseScn 0 for new records
               payload, clientUpdatedAt, deleted } ] }   // <= 200 changes/batch
-> 200 { results: [ { id, status: "accepted", newScn }
                  | { id, status: "conflict", current: <record> }
                  | { id, status: "rejected", error: <code>, pointer: <json-pointer> } ] }
-> 426 upgrade_required   // whole batch. PULL still works - never lock a user out of their own data.
```

`clientUpdatedAt` more than 24h in the future is clamped server-side and the accepted result
carries `"clamped": true`, so the client can warn.

## The rule this task exists to honour

`docs/SYNC.md` line 7, quoted because it is the whole design:

> Conflicts are resolved record-level last-writer-wins on the client - **except `Vehicle`, which
> merges field-level** so a stale device cannot revert a setting the user deliberately changed
> (S9, hard rule 13) - then re-validated by the domain rules (the odometer timeline check catches
> what LWW can't).

**S9 is the load-bearing invariant of this task**, and the reason it gets its own scenario is that
its failure is *invisible*:

> The user corrects the Volvo's tank capacity 71 -> 60 L on the iPhone on Monday. The iPad has not
> synced for a week and still holds 71. On Friday the iPad renames the car "Volvo" -> "V60" - an
> unrelated field - and pushes. **Transport:** field-level merge on `Vehicle`. The iPad's write
> covers `name` only; `tankCapacityL` keeps the iPhone's newer value. Merged result:
> `name = "V60"`, `tankCapacityL = 60`. **Under record-level LWW the iPad's whole row would win
> and the correction would silently revert to 71.**

`docs/SYNC.md` names the fields this covers: `tankCapacityL`, `initialOdometer`, `homeCurrency`,
`units`, `paceLimitKmPerDay` - "all user decisions, all feeding calculations, all edited
independently". A reverted tank capacity produces no badge, no toast and no wrong-looking number,
just partial-fill maths that is quietly wrong from then on.

## The testability constraint – read before designing

`URLSession` cannot be asserted against in a unit test, and there is no server in `swift test`.
So the **merge decisions must be pure value types in `TankbookCore`** and the network must be an
injected protocol. This is the same split that made `ReminderNotificationPlan`, `TabBarMetrics`,
`PumpPhotoGate` and `ServiceEntryDraft` testable, and it is the only reason P3.6 could prove
"exactly one overdue follow-up" *as a loop*.

Concretely: a `SyncMerge` (or similarly named) pure function that, given a local record, a remote
record and the entity type, returns what to keep - and for `Vehicle`, which fields to keep from
which side. **The S1-S9 suite asserts that function and a deterministic in-memory transport
double, not `URLSession`.**

**A design that puts merge logic inside a networking call site is not acceptable here**, because
it cannot be tested and the phase gate requires it to be. `AppTabBar`'s padding arithmetic lived
in the app target for two whole phases and its double-counted inset survived both, precisely
because the package tests could not import it.

## What to build

1. **The dirty queue**: collect `dirty` rows, batch at **<= 200 changes**, mark `pushing`, and
   return them to `dirty` on any failure. Idempotent - a retried batch must not double-apply.
2. **The pull loop**: paginate on `nextSince`, **persist the cursor only after the page is
   applied**, and follow `more`. A cursor advanced one past the last applied record loses history -
   that exact bug was caught on the server side in P4.2, so do not reintroduce it here.
3. **The merge**, pure and per entity type: record-level LWW by `clientUpdatedAt` for everything,
   **field-level for `Vehicle`**. On `conflict` from push, re-merge against the returned `current`
   and re-push, with **bounded** retries (S6: "fully automatic", and "Screens: nothing, ever").
4. **Domain re-validation after merge**: the merged timeline is re-checked and S3's out-of-order
   entry gets its amber `ConflictState` - transport accepted both records, the domain is what
   flags one.
5. **The S7 posture**: every write lands locally and queues; **no screen is ever sync-gated**
   (hard rule 1) and there are no banners or toasts during an outage - only the passive
   "Waiting to sync · 5 changes" row. Do not add a modal anywhere.
6. **`410` handling**: device revoked or account deleted -> re-onboard or detach. **Local data
   stays local** - a `410` deletes nothing.
7. **`426` handling**: the push batch is refused, **pull still works**. Never lock a user out of
   their own data.

**The L3 suite: one deterministic test per scenario, S1 through S9.** Not one test with nine
assertions - nine named tests, each reproducing its scenario against the in-memory transport.

Specific shapes that must hold:

1. **S9 (the one that matters)**: stale device writes `name`, fresh value of `tankCapacityL`
   survives. Assert the merged `Vehicle` has **both** `name == "V60"` **and**
   `tankCapacityL == 60`. Then assert the same scenario for `initialOdometer`, `homeCurrency`,
   `units` and `paceLimitKmPerDay` - `docs/SYNC.md` names all five, and a merge that special-cases
   one field is not field-level merge.
2. **S1**: record-level LWW on an entry. The **documented** outcome stands - the iPhone's odometer
   edit **is lost** and the losing version lands in the local undo log. Assert the loss, not an
   absence of conflict.
3. **S4**: both directions. Edit newer -> the record **resurrects with the edit**; delete newer ->
   it stays deleted and the edit goes to the undo log. Two tests or two cases, never one.
4. **S6**: a `conflict` result triggers re-merge and re-push, automatically, and retries are
   **bounded** - assert the bound by making the server conflict forever and showing the client
   stops.
5. **S3**: after merge, the out-of-order entry carries the amber `ConflictState` and its segment
   is excluded from the headline.
6. **S7**: with the transport failing every call, every local write still lands, nothing is
   sync-gated, and the queue drains on recovery in `pull -> merge -> push` order.
7. **Cursor safety**: a page applied then a crash before the next page must not skip records.
   Assert by applying page 1, discarding the client, and resuming from the persisted cursor.
8. **Batch cap**: 250 dirty rows produce two batches, not one of 250.

### Vacuous-assertion traps for this task

- `#expect(true)`, or asserting only that a call did not throw.
- **Testing S9 with an on-time device.** If the stale device's write is newer on every field, LWW
  and field-level merge give the same answer and the test proves nothing. The stale device must be
  **older on the field it is not writing**.
- Asserting the merge result **exists** without asserting **which side each field came from**.
- Building the expected merged record by calling the same merge function under test. Write the
  expected values as **literals**.
- Mocking the merge and asserting the mock. The merge **is** the logic.
- An S6 test that never actually re-pushes, or one that would loop forever if the bound were
  removed - assert the bound.
- A "queue" test that never asserts rows returned to `dirty` after a failed push.
