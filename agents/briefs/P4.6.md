## The rules this task exists to honour

`docs/SYNC.md` -> "Attachments: the blob pipeline", quoted where it is normative:

> **What gets uploaded:** a *sync rendition* - JPEG, **long edge <= 2048 px, quality ~80**
> (~200-600 KB). The full-resolution original **stays on the capturing device**; it is never needed
> for OCR (which already ran) or cross-device viewing. **PDFs pass through unmodified, capped at
> 10 MB.** A tiny thumbnail (**~120 px, ~5 KB, base64**) travels *inside* the Attachment record
> payload itself, so lists render photo chips instantly with **zero blob fetches**.

The upload order is the load-bearing part:

```
1. Client computes sha256 of the rendition.
2. POST /blobs/begin { sha256, size, contentType }
   -> { status: exists }  |  { status: upload, url, expires: 15 min }  |  413 | 429
3. Client PUTs the bytes directly to the presigned URL (resumable retry: just re-begin).
4. POST /blobs/commit { sha256 } -> server verifies object + size.
5. Only THEN does the entry referencing it push - records never point at blobs the server can't serve.
```

> **Step 5 is an invariant, not a suggestion.** A record that references a blob the server cannot
> serve is a broken entry on every other device.

Delivery:

> After a pull, the client fetches missing blobs **lazily**: thumbnails are already in payloads;
> the full rendition downloads when the user **opens** the entry (or eagerly on Wi-Fi, a setting).
> `GET /blobs/{sha256}` -> `302` to a short-lived presigned GET. **The device caches the file
> locally forever after - content addressing means no revalidation, ever.**

> Uploads queue offline like everything else (S7): the entry syncs **text-first with the blob
> pending**, and other devices show the thumbnail with a **"photo syncing" shimmer** until the blob
> lands.

## The testability constraint – read before designing

There is no server under `swift test`, and image encoding is slow. So:

- the **decisions** (what to upload, in what order, when to download, what to cache) must be
  **pure value types in `TankbookCore`**, and
- the network must be an **injected protocol** with a recording double,

the same split that made `RecordMerge`, `ReminderNotificationPlan`, `TabBarMetrics` and
`PumpPhotoGate` testable. A design that puts upload ordering inside a `URLSession` call site
cannot be tested, and the ordering invariant above is exactly what must be proved.

## What to build

1. **Rendition generation**: JPEG, long edge **<= 2048 px**, quality ~0.8. An image already under
   2048 px is not upscaled. **PDFs pass through unmodified**, capped at 10 MB.
2. **The inline thumbnail**: ~120 px, ~5 KB, base64, carried **inside the Attachment record
   payload** so a list renders with **zero blob fetches**.
3. **The upload chain, in order**: sha256 -> `begin` -> PUT -> `commit` -> **only then** the
   referencing record pushes. Handle `exists` (dedupe: skip the PUT entirely), `413`, `429`.
4. **Lazy download**: on pull, blobs are **not** fetched. The full rendition downloads when the
   entry is opened, or eagerly on Wi-Fi behind a setting.
5. **Verify on download**: the bytes fetched from `GET /blobs/{sha256}` **must hash to the sha256
   that was asked for**. If they do not, discard them - do not cache, do not display. Content
   addressing is only a guarantee if it is checked.
6. **Cache forever after**: a verified blob is never re-fetched or revalidated.
7. **The "photo syncing" state**: an entry whose blob has not landed shows the thumbnail with a
   shimmer, and is **fully usable** - nothing is blocked on a photo (hard rule 1).
8. **Strings** through the String Catalog, EN **and** RU. **Read the rule at the top of
   `ios/App/Sources/Localization/L10n.swift` first** - `Text(_: String)` does not localise, so an
   expression mixing runtime data and copy renders its English key while the gate stays green. Six
   bugs have shipped that way.

## Tests

Counts on your branch before you start: `swift test` **619**, `xcodebuild test` **123**. Run both
first, record the real numbers, and both must rise.

1. **The ordering invariant** (L1): a record referencing a new blob **does not push until commit
   has succeeded**. Assert the **transport call order**, not that both eventually happened. This is
   the test the whole task exists for.
2. **Commit fails -> the record still does not push**, and the upload is retried later. The
   negative half of 1.
3. **Dedupe**: `begin` answering `exists` **skips the PUT entirely** - assert the PUT was never
   issued, not merely that the flow completed.
4. **Rendition caps**: a 4000 px image comes out **<= 2048 px** on its long edge; a 1200 px image
   is **not upscaled**; a PDF passes through **byte-identical**; an 11 MB PDF is refused.
5. **The thumbnail rides in the payload**: a list renders from the record alone with **zero blob
   fetches** - assert the download call count is 0.
6. **Verify-on-download**: bytes whose hash does not match the requested sha256 are **discarded** -
   not cached, not displayed. **Test the corrupt case, not just the happy one.**
7. **Lazy**: a pull fetches **no** blobs; opening the entry fetches exactly one.
8. **Offline (S7)**: the entry saves and syncs **text-first** with the blob pending, and the app is
   fully usable.
9. **L4**: the "photo syncing" shimmer renders, and the entry is openable and editable while it is
   showing.

### Vacuous-assertion traps for this task

- Asserting commit and push both happened without asserting **commit came first**. The ordering is
  the invariant; a test blind to order passes a broken implementation.
- A verify-on-download test with only a matching hash.
- A dedupe test that asserts the flow succeeded rather than that **the PUT never happened**.
- Testing the 2048 px cap with an image already under 2048 px.
- Asserting the shimmer exists without asserting the entry is **usable** while it shows.
- Mocking the sync engine and asserting the mock.
