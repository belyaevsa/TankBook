## Why this task gets engineered redundancy rather than good copy

`docs/JOURNEYS.md` F7, verbatim - and read the parenthetical:

> **F7 · Restore fails or comes back empty (J11's nightmare).** New phone, sign-in works, but the
> backup is missing, corrupt, or the backend is down. **The category's fatal moment - this journey
> gets engineered redundancy, not just good copy.**

> - Restore sources, tried in order and shown honestly: **sync pull from zero** (the normal path)
>   -> a **server backup snapshot** -> **"import a file you exported yourself."**
> - If the backend is down: say **exactly that** ("sync service unreachable - you can import an
>   export file, or your data will arrive as soon as it's back"), **never a generic "something went
>   wrong."**
> - If truly nothing is found: the app says so **before the user logs anything new** (an empty
>   garage with "expecting your data? ->" recovery entry point), **because the worst sequence is:
>   user re-adds car manually, backup later reappears, and now there's a merge problem.**
> - **Post-restore: show the same verification stats as J2** (entries, date range, last odometer)
>   so trust is re-established **with numbers, not a checkmark**.

That third bullet is the subtle one and the reason this is not just a progress screen. **An empty
restore that lets the user start typing creates a merge conflict that did not have to exist.** The
recovery entry point exists to prevent a data problem, not to be reassuring.

`docs/VISION.md` names the graveyard this avoids: Fuelly and Мой Авто both lost users here.
**Restore must be boringly reliable and tested in CI**, with the local export always available as
the user-held fallback.

## The mechanism is already built – this task is the chain, not a new engine

`docs/SYNC.md`:

> **Pull:** strictly ordered by SCN, paginated, cursor stored per device (`last_pull_scn`). A
> device that was offline for a year just replays the stream. **Fresh install + sign-in = pull
> from 0 (this IS restore).**

> New-device restore: **text records first** (the garage is usable in seconds), **blobs trickle in
> background by recency. Restore never blocks on photos.**

`docs/API.md`: *"Fetching the latest data IS pulling from a cursor of 0 - fresh install/restore
and incremental catch-up are the same call."*

**So there is no separate restore protocol.** If you find yourself writing one, stop.

## What to build

1. **Restore = pull from cursor 0**, driven by the existing `SyncEngine`. Text records land first
   and the garage becomes usable; **photos never block it**.
2. **Resume after interruption.** A restore killed mid-stream resumes from the persisted cursor
   **without losing or duplicating records**. The cursor is persisted **only after a page is
   applied** (P4.5's rule) - restore is where that rule earns its keep.
3. **The three sources, tried in order and shown honestly**: pull from zero -> server snapshot ->
   import your own export. When the backend is down, say **exactly that**, with its next step
   (hard rule 7) - never a generic failure.
4. **The empty-restore recovery entry point**: if nothing is found, the app says so **before** the
   user can log anything, and offers "expecting your data? ->". This is the merge-conflict
   prevention, not a nicety.
5. **Post-restore verification stats**: entries, date range, last odometer with its source device -
   **numbers, not a checkmark**.
6. **Strings** through the String Catalog, EN **and** RU. **Read the rule at the top of
   `ios/App/Sources/Localization/L10n.swift` first** - `Text(_: String)` does not localise, so an
   expression mixing runtime data and copy renders its English key while the gate stays green. Six
   bugs have shipped that way, and "1 240 entries · Mar 2019 - Aug 2026" is exactly that shape:
   a full localised phrase per language, never concatenation, with Russian plural rules.

## Tests

Counts on your branch before you start: run `swift test` and `xcodebuild test` first and record the
real numbers. Both must rise.

**The L3 headline: pull-from-zero produces a dataset that hash-equals the origin.** Seed an origin
device, push everything, restore into a fresh device from cursor 0, and assert the restored records
**hash-equal** the origin's - not "the same count", not "the first entry matches". A count-only
assertion passes a restore that silently drops a field.

1. **Hash-equals-origin** (above).
2. **Interrupted restore resumes**: kill after page 1, resume, and assert the final dataset still
   hash-equals the origin - **no loss, no duplication**. Run the interruption at a page boundary
   *and* mid-page.
3. **Restore never blocks on photos**: with the blob transport failing every call, the garage is
   still usable and every text record still lands.
4. **Backend down** produces the F7 copy naming its next step, **not** a generic error - assert the
   string, and assert the import path is reachable from it.
5. **Empty restore** reaches the recovery entry point, and does so **before** any "add a car"
   affordance is usable. **Assert the ordering**, because the whole point is preventing the user
   from typing first.
6. **Verification stats are real numbers** derived from what landed - seed a known dataset and
   assert the literal counts and date range.
7. **L4**: the Restoring screen renders its progress, its server-down state, and its empty state.

### Vacuous-assertion traps for this task

- Asserting a **count** instead of a hash. The failure this test exists to catch is a *field*
  silently dropped, which a count cannot see.
- An interrupted-restore test that interrupts only at a page boundary.
- Asserting the empty-restore card **exists** without asserting it appears **before** the user can
  add a car.
- Asserting "an error is shown" rather than the specific F7 copy and its next step.
- A photos test where the blob transport succeeds.
- Mocking `SyncEngine` and asserting the mock. Restore **is** the engine pulling from 0.
