## The rules this task exists to honour

`docs/NOTIFICATIONS.md` is the authority, quoted where it is normative:

> **Remote push (APNs via our backend) - carries only silence.** One use in v1.x: the **silent sync
> nudge** (`content-available`, no alert, no sound, no text - the payload says only "pull").

> **No user-visible remote push exists at all in v1**, and no marketing push will ever exist -
> written as a hard rule.

> nudges are an optimization, **never a dependency** - foreground polling is the always-there
> fallback.

> Device tokens register via `PUT /account/devices/{id}/push-token`; **token invalidation (APNs
> feedback) just clears the row - the device falls back to polling.**

The scenario catalog pins the throttle:

| Sync nudge | Silent APNs | Invisible, **throttled server-side (max ~1/15 min per device)** |
| Config nudge | Silent APNs (`config: true` hint on the same payload) | propagates an urgent change such as a kill switch in minutes rather than the normal 6-hour poll |

**The nudge is an optimization** is the load-bearing sentence. If every nudge were dropped, every
device must still converge by polling. Nothing may become unreachable because a push failed.

## What to build

1. **An injected APNs client interface** with a real implementation (token-based JWT auth,
   `content-available: 1`, no alert/sound/badge) and a **recording double** for tests. Same shape
   as `IBlobStorage`.
2. **Nudge on push**: when a device's `POST /sync/push` is accepted, the account's **other**
   devices get a silent nudge. **Never the pushing device itself** - it already has the data, and
   nudging it is a wakeup that buys nothing.
3. **The throttle: at most ~1 nudge per 15 minutes per device**, server-side, configurable.
   Bursts collapse: ten pushes in a minute produce **one** nudge per sibling device, not ten.
4. **Token invalidation clears the row.** An APNs rejection that means "this token is dead"
   (`BadDeviceToken`, `Unregistered`) clears `push_token` and the device silently falls back to
   polling. A **transient** failure (5xx, timeout) must **not** clear the token - that would
   downgrade a healthy device to polling forever on one bad minute. **These two cases must be
   distinguished.**
5. **Failure is never fatal to sync.** A push that cannot be delivered - no token, APNs down,
   throttled - changes nothing about correctness. `POST /sync/push` still returns its normal
   result, and the nudge is best-effort and out of band.
6. **The config-nudge hint**: the same payload may carry `config: true` to propagate an urgent
   config change. Wire the flag; do not build a config-change detector.

## Tests (L2, against real Postgres via Testcontainers)

Count now: `dotnet test` **179**. Run it first, record the real number, and it must rise.

1. **The pusher is not nudged; its siblings are.** Two devices, one pushes: assert the recording
   client saw exactly one nudge, addressed to the *other* device.
2. **The throttle collapses a burst**: ten pushes inside the window produce **one** nudge per
   sibling. Assert the count, not that "a nudge happened".
3. **The throttle reopens**: past the window, a further push nudges again. Drive the clock through
   an injected `TimeProvider`; **do not sleep**.
4. **A dead token clears the row**; the device is not nudged again and its next pull still works.
5. **A transient failure does NOT clear the token** - this is the half that a lazy implementation
   gets wrong, and it is the difference between a blip and a device stuck on polling forever.
6. **No token, no nudge, no error**: a device that never registered one is skipped silently and
   `POST /sync/push` is unaffected.
7. **APNs completely down: push still succeeds.** Assert the endpoint's normal 200 and the
   accepted results, proving the nudge is out of band (the "never a dependency" rule).
8. **The payload is silent**: assert it carries `content-available` and **no `alert`, `sound` or
   `badge` key**. Assert the absence explicitly - this is the v1 hard rule expressed as a test.
9. **No push token in any log line** (hard rule 12), swept through `WithoutMachineFields()`.
10. **Any new migration applies and rolls back.**

### Vacuous-assertion traps for this task

- Asserting "a nudge was sent" without asserting **to whom**. The pusher-excluded rule is the
  one most easily broken.
- A throttle test that sends **two** pushes. Two could pass by accident; send ten and assert one.
- Testing the throttle with `Thread.Sleep`. Inject `TimeProvider`.
- Treating every APNs failure as fatal to the token - test 5 exists precisely to catch that.
- Asserting the payload *contains* `content-available` without asserting it **lacks** `alert`.
- Mocking the repository and asserting the mock. These are L2 tests against real Postgres.
