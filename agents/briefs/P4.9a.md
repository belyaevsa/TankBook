## The contract, verbatim from `docs/API.md` (the authority)

| Endpoint | Auth | Contract |
|---|---|---|
| `GET /account/devices` | bearer | Registered devices with `lastSeenAt` - the "manage devices" screen. |
| `PUT /account/devices/{id}/push-token` | bearer | `{ apnsToken }` (or `{ fcmToken }` for Android later) -> `204`. Enables silent sync nudges (`NOTIFICATIONS.md`); APNs invalidation clears the row and the device falls back to polling. |
| `DELETE /account/devices/{id}` | bearer | Revoke a device: its next pull gets `410`. |
| `DELETE /account` | bearer | Tombstone account; purge records + blob prefix after grace period (SYNC.md). Devices get `410`; **local data stays local**. |

`docs/SYNC.md` line 330 is the normative sentence for deletion:

> Account deletion: tombstone the account, purge `records`/`blobs` after grace period; devices get
> `410` -> **local data stays local** (the user keeps their log; it just stops syncing).

That last clause is the rule this task exists to honour. **`DELETE /account` deletes nothing on
the device.** It tombstones server-side, the devices learn via `410`, and the user still has their
whole log locally (hard rule 1: no screen is ever sync-gated). A server that expects the client to
wipe itself would be a bug.

## What to build

1. **`GET /account/devices`** - this account's devices with `lastSeenAt`. Never another account's,
   and never a revoked device presented as active.
2. **`PUT /account/devices/{id}/push-token`** - store it; `204`. **Clearing must be expressible**
   (a null/absent token empties the row), because APNs invalidation is how a device falls back to
   polling. A device id belonging to another account is **`404`**, not `403`.
3. **`DELETE /account/devices/{id}`** - revoke, via the existing chain revocation. Its next pull
   gets `410`. Other devices keep working, and **no records are deleted**.
4. **`DELETE /account`** - tombstone (`accounts.deleted_at`), revoke every device so all of them
   get `410`, and schedule the purge for after the grace period. **It deletes no records
   synchronously** - the grace period is the whole point.
5. **The purge job** - a hosted background service that, past the grace period, purges tombstoned
   accounts' `records` and calls `BlobService.PurgeAccountAsync`. It must also be **invocable
   directly** so an L2 test can run one pass without waiting on a timer.
   **The timer must not run inside `WebApplicationFactory` test hosts** - P4.3 explicitly declined
   to add one for that reason. Register it so the tests drive the method, not the clock.
6. **The orphan sweep** gets the same treatment: reachable from the same job, per account.

## Tests (L2, against real Postgres via Testcontainers)

Count now: `dotnet test` **169**. Run it first, record the real number, and it must rise.

1. **Deletion is a tombstone, not a delete**: immediately after `DELETE /account`, the account's
   `records` rows still exist and `deleted_at` is set. **Assert the rows are still there** - this
   is the "local data stays local" guarantee's server half, and a test that only asserts a 2xx
   misses it entirely.
2. **Every device gets `410` after account deletion**, through the same path a revoked device
   takes. Two devices, both `410`.
3. **Revoking ONE device leaves the others working** - the second device's pull still succeeds,
   and no records were deleted.
4. **The purge fires only past the grace period**: an account tombstoned *within* the window
   survives a job pass with its records and blobs intact; one tombstoned *past* it is purged,
   records and blob prefix both. **The surviving case is the half that matters** - a job that
   purges everything passes a purge-only test.
5. **Cross-account device access is `404`**: account B cannot read, revoke or set a push token on
   account A's device. Assert **nothing changed** on A's row, not only the status.
6. **Push token round-trip and clearing**: set, read back, clear, and confirm the cleared row is
   empty rather than holding a stale token.
7. **`GET /account/devices` never lists another account's devices** and marks revoked ones
   accordingly.
8. **No token, push token or email in any log line** (hard rule 12), asserted against captured log
   output through `WithoutMachineFields()`.
9. **Any new migration applies and rolls back.**

### Vacuous-assertion traps for this task

- Asserting a status code without asserting **what changed in the database** - especially for
  deletion, where the correct behaviour is that records **remain**.
- A purge test with no surviving case (see 4). A job that deletes everything is not a job with a
  grace period.
- Testing `410` for the deleting device only, and not for its siblings.
- A cross-account test that asserts `404` but not that the target row was untouched.
- Mocking the repository and asserting the mock. These are L2 tests against real Postgres.
- Driving the purge by sleeping until a timer fires. Call the method.
