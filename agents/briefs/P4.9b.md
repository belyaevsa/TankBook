## The sync surface – normative, `docs/SYNC.md` -> "The Settings sync surface"

Read that section in full before writing. The three parts and their rules:

1. **Status, always present when signed in.** Relative: "Synced just now", "Synced 3 hours ago",
   or "Waiting to sync · 5 changes" plus "Will sync when you're back online" when offline. It is
   **reassurance, never a warning** - it does **not** turn amber with age. A long queue is not an
   error state; a week offline is the same as an hour (S7).
2. **"Sync now"** - a manual trigger, never a requirement:
   - **Idempotent**: inert while a sync is in flight, so a repeated tap is **never a second push**.
   - **Offline is not an error**: the row settles back to "Will sync when you're back online".
     The tap is never punished with an error.
   - **Failure names its next step** (hard rule 7) and the automatic retry continues regardless.
   - **It may never be the only path to a synced state** (hard rule 1). Deleting the button must
     change nothing about whether data eventually arrives.
3. **Issues, split by class** - this is the part that is easy to get wrong:
   - **Transport** (410 revoked, blob quota 429, server down): **belongs here**, as a card with its
     next step. It is about the account.
   - **Domain** (S1-S5 flagged records): belongs **where the data lives**, as a badge (hard rule
     8). Settings shows **a count and a link only** - "2 entries need a look" navigating to the Log
     filtered to flagged entries - and **resolves nothing itself**.

   **The count is derived, never stored**: the number of records carrying a `ConflictState`,
   recomputed like every other statistic (hard rule 2's principle). A stored counter drifts out of
   agreement with the badges and then two surfaces disagree about the same data.

**A resolution control in Settings is a bug**, not a nicety: it tears a conflict out of the
context that makes it decidable, asking the user to adjudicate an odometer discrepancy with no
entry in front of them.

## Tests

Counts on your branch before you start: `swift test` **593**, `xcodebuild test` **115**. Run both
first, record the real numbers, and both must rise.

1. **The count is derived** (L1): it equals the number of records carrying a `ConflictState`;
   resolving a conflict elsewhere changes it with **no write to Settings**. Assert the recomputed
   value, not a stored field.
2. **"Sync now" is idempotent** (L1): tapping while a sync is in flight issues **no second push** -
   assert the **transport call count**, not the button's enabled state. A disabled button that
   still queues a push passes a UI-state assertion and fails the rule.
3. **Offline "Sync now" is not an error** (L1/L4): produces the waiting copy, no error surface.
4. **Status never turns amber with age** (L1): a queue hours or a week old renders in the ordinary
   status colour. Assert the token, not a screenshot.
5. **L4, every state renders**: guest, synced, pending, revoked, quota, flagged.
6. **L4, the flagged row navigates** to the filtered Log, and **Settings contains no resolution
   control** - assert the absence.
7. **Localization gate** exit 0, RU 100%.

### Vacuous-assertion traps for this task

- `#expect(true)`, or asserting a row exists without asserting what it says.
- Testing "Sync now" idempotency via `isEnabled` instead of the **push count**.
- Testing the flagged count with **zero** conflicts only - it passes on a hardcoded 0.
- Asserting the derived count by calling the same function the view calls. Seed known conflicts
  and write the expected number as a **literal**.
- A "no resolution control" test that never asserts an absence.
