## The rule this task exists to serve

`CLAUDE.md` hard rule 3: **Money is a pair** - original + home currency with a rate snapshot;
**`rateDate` = entry date, never "today"**; snapshots immutable, backfill fill-blanks-only.

`docs/SCHEMA.md` line 93 states it as a comment on the model itself:

> `rateDate = entry.date` (the day it happened), **NEVER "today"** - a wrong-date rate is worse
> than none (F9).

That is why this service is **keyed by date** and why carry-forward is stored **per date** rather
than resolved at read time. `docs/SCHEMA.md` line 418 is the normative description:

> Updated by a daily background job (ASP.NET hosted service, ~17:00 CET after ECB publishes): ECB
> reference rates for the majors, plus a CIS source (CBR/NBK or a commercial feed) for
> RUB/KZT/AMD/GEL/BYN - the gap ECB left. **Weekends/holidays carry the last published rate
> forward, stored per-date so `rateDate` lookups are exact.** Manual correction path for a bad
> feed day (soft-delete + re-fetch); **rows are append-only otherwise - snapshots in entries mean a
> correction never rewrites user history.**

**Read that twice.** A Saturday fill-up must resolve to a rate row **dated Saturday** carrying
Friday's published value - not "no row, ask the client to look backwards". The client asks for one
date and gets one answer.

## The contract, verbatim from `docs/API.md`

| Endpoint | Auth | Contract |
|---|---|---|
| `GET /rates?date=&base=` | public | All quotes for one date. Past dates: `Cache-Control: immutable`. |
| `GET /rates/pack?from=&to=&base=` | public | Bulk range for device cache / seed refresh. |

Conventions that apply: JSON bodies, ISO-8601 UTC dates, RFC 7807 problem+json for errors
(`{ type, title, status, detail }`), `429` with `Retry-After` for rate limits.

**`Cache-Control: immutable` is for PAST dates only.** Today's row can still change (a late
publish, a correction); yesterday's cannot. Serving today as immutable poisons every CDN and
device cache with a value that was provisional.

## What to build

1. **The feed seam**: an interface per source (or one with a source enum), a real ECB
   implementation and a real CIS implementation behind it, and a **recording/scripted double** for
   tests.
2. **The daily job**: fetches, upserts rows, and **materialises carry-forward** - for every date in
   the covered range with no published quote (weekend, holiday), write a row **dated that day**
   carrying the last published value, with `source` making clear it was carried forward. It must
   be **invocable directly** so an L2 test runs one pass without a timer, and its timer must not be
   registered in test hosts.
3. **Idempotence**: running the job twice for the same day changes nothing and duplicates nothing.
   It will be re-run; that is normal, not an error.
4. **Append-only, with a correction path**: an ordinary re-fetch never rewrites a published row.
   The documented manual correction is **soft-delete + re-fetch**. A correction must never mutate
   history in place, because entries hold snapshots and a rewritten rate would silently disagree
   with them.
5. **`GET /rates?date=&base=`**: all quotes for that date. **Past dates get
   `Cache-Control: immutable`; today does not.** ETag like `/config`.
6. **`GET /rates/pack?from=&to=&base=`**: bulk range, bounded - reject an absurd range with a 400
   rather than streaming ten years.
7. **Missing/un-fetched date**: answer honestly (404 or an empty quote set per your design, stated
   in your report). **Never invent a rate**, and never silently substitute a neighbouring date's
   value in the response body - carry-forward is a stored row with its own date, not a read-time
   guess.

## Tests (L2, against real Postgres via Testcontainers)

Count now: `dotnet test` **190**. Run it first, record the real number, and it must rise.

1. **Weekend carry-forward**: Friday publishes, Saturday and Sunday have **stored rows dated
   Saturday and Sunday** with Friday's value. Assert the **rows exist with those dates**, not that
   a lookup happens to return something.
2. **Holiday carry-forward** across a multi-day gap - two consecutive non-publishing days both get
   rows.
3. **Idempotent job**: two passes over the same day leave exactly one row per (date, base, quote)
   and identical values. Assert the **row count**.
4. **Append-only**: a re-fetch with a *different* value does not rewrite the published row.
   Assert the original value survives. This is the rule that protects user history.
5. **The correction path** does what it documents (soft-delete + re-fetch), and the corrected row
   is distinguishable from an ordinary one.
6. **`immutable` only for past dates**: a past date's response carries it, **today's does not**.
   Assert both halves - a test that only checks the past date passes an implementation that marks
   everything immutable.
7. **`/rates/pack` range**: returns the full inclusive range; an absurd range is rejected.
8. **A date with no data does not invent one** - assert the documented empty/404 answer.
9. **Both endpoints are reachable without a bearer token.**
10. **Any new migration applies and rolls back.**

### Vacuous-assertion traps for this task

- Asserting carry-forward by calling a lookup helper that itself does the look-back. The point is
  that the **row exists with that date**; query the table directly.
- An idempotence test that runs the job once.
- Testing `immutable` on a past date only (see 6).
- A feed test that hits the real ECB. It will fail in CI and pass locally, or the reverse.
- Mocking the repository and asserting the mock. These are L2 tests against real Postgres.
- Asserting a 200 without asserting the quotes in the body.
