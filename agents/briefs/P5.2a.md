## The rule this task exists to serve

`CLAUDE.md` hard rule 3: **money is a pair** – original + home currency with a rate snapshot;
**`rateDate` = the entry date, never "today"**; snapshots immutable, backfill **fill-blanks-only**.

`docs/SCHEMA.md`, verbatim and normative:

> `rate` is ORIGINAL per HOME: `homeAmount = amount / rate` (289.50 / 4.2706 = 67.79, rounded to
> the home currency's minor units)
> `rateDate = entry.date` (the day it happened), NEVER "today" – a wrong-date rate is worse than
> none (F9).
> `homeAmount` is a SNAPSHOT: written once when the rate is known, immutable afterwards; later
> feed updates never touch it.
> Backfill rule (rate arrives later, incl. via sync on another device): fill ONLY if `homeAmount`
> is nil; never recompute an existing snapshot.

`docs/SYNC.md` S8, verbatim:

> conversion backfill is **fill-blanks-only** … any device may write `homeAmount`/`rate` when they
> are nil, and no device ever recomputes an existing snapshot. Both devices backfilling
> concurrently write identical values (same feed, same `rateDate` = entry date), so the LWW winner
> is byte-equivalent – no user-visible effect.
> **The rate cache itself never syncs** – each device fetches its own feed; only `Money` snapshots
> inside entries travel. A device with no feed access simply leaves entries pending; stats exclude
> them from home-currency sums with the F9 footnote until any device fills them.

`docs/JOURNEYS.md` F9, verbatim:

> Entry always saves with the original amount – conversion is metadata, never a save-blocker.
> Rate arrives later → conversion fills in; rate *never* exists (feed gap) → entry shows original
> currency in trends with a footnote count ("3 entries pending rates"), and **the user may set a
> manual rate per entry**.
> ⚠ Never apply today's rate to last month's fill-up silently: a wrong-date rate is worse than no
> rate.

**The two halves of that rule pull in opposite directions and both must hold.** A *feed* fills
blanks only and may never touch a written snapshot. A *user* setting a manual rate is hard rule 13
– the app suggests, the user decides – and **must** be able to replace a snapshot the feed wrote.
If you implement one override path used by both, you have broken one of them.

## The wire contract – verbatim from the shipped server, `backend/src/Tankbook.Api/Rates/RateEndpoints.cs`

`GET /v1/rates/pack?from=&to=&base=` – **public, no auth, no account.** `from`/`to`/`base` are
required; `from` after `to` is a 400, and a range longer than `RateOptions.MaxPackDays` is a 400.
Errors are RFC 7807 problem+json. Response body, camel-cased by
`JsonSerializerDefaults.Web`, with `DateOnly` rendering as `yyyy-MM-dd`:

```json
{ "from": "2026-08-01", "to": "2026-08-27", "base": "EUR",
  "rates": [ { "date": "2026-08-21", "quote": "PLN", "rate": 4.2706, "source": "ecb" } ] }
```

`GET /v1/rates?date=&base=` (single day, ETag + `If-None-Match` + 304) also exists. **It is out of
scope** – the client keeps a ~2-year rolling cache, so the pack endpoint is the only one it needs.
Do not implement the single-date one "for completeness".

### Two things about that body will silently corrupt money if you skim them

1. **`rate` is a JSON NUMBER, and Swift's default `Decimal` decoding can route it through
   `Double`.** `4.2706` as a `Double` is not `Decimal(string: "4.2706")`. This is exactly why the
   bundled seed pack types `rate` as a JSON *string* – read the comment on `ExchangeRateSeed`. The
   wire cannot be changed (it is a shipped, merged public endpoint), so **the client must decode
   the number exactly**, e.g. by decoding the raw token text and going through
   `Decimal(string:locale: en_US_POSIX)`, or any approach you can prove. **Prove it with a test
   that fails under the naive decode**, not with a comment.
2. **`source` is not always `"ecb"` or `"cis"`.** A carried-forward row (weekend, holiday) is
   written by the server as `source + ":carried-forward"` – see
   `backend/src/Tankbook.Api/Rates/IRateFeed.cs`, `RateSources.Carried`. The existing seed decoder
   maps `row.source == "cis" ? .cis : .ecb`, so **`"cis:carried-forward"` silently becomes `.ecb`
   today.** Put the wire→`RateSource` mapping in **one** shared place, use it from both the seed
   decoder and the pack decoder, and cover all four strings plus an unknown one.

## What NOT to explore – closed questions

- **Whether the rate cache syncs.** It does not, ever (S8). Only `Money` snapshots inside entries
  travel, through the ordinary dirty/push path.
- **Whether a rate miss is an error.** It is not. A miss, a network failure, a 400 and a garbage
  body are all **silent** – the entry stays rate-pending and the app is fully usable offline
  (hard rule 1, F9). No new error type reaches a screen from this task.
- **Whether to look a rate up backwards from a neighbouring date.** No. The server materialises
  carry-forward as a stored row **dated that day**, so the client asks for one date and gets one
  answer. Do not add read-time look-back.
- **Recompute plumbing.** Stats are derived on read (hard rule 2) – there is nothing stored to
  invalidate. Backfilling a `homeAmount` changes cost/km on the next read by construction; your job
  is to *assert* that, not to build a recompute pipeline.
- **The single-date `/rates` endpoint, ETag/304, the paywall, and all UI.** Out of scope.

## What to build

1. **`RemoteRateFetcher`** in `ios/Sources/TankbookCore/Rates/`, conforming to the existing
   `RateFetcher` protocol, over `TankbookHTTPClient` in the shape of `RemoteSyncTransport`.
   Builds the `from`/`to`/`base` query, decodes the pack body **exactly** (trap 1), maps `source`
   through the shared mapping (trap 2), and turns **every** failure – transport error, non-2xx,
   problem+json, malformed body – into a thrown error that `RateStore.refresh()` already swallows.
   The host allowlist must still be enforced before any I/O.
2. **One shared wire→`RateSource` mapping**, used by both `RateSeedStore.decode` and the pack
   decoder. Fix the `"cis:carried-forward"` misclassification in the same change.
3. **Persistence for the cache.** The store is in-memory and dies with the process. Give
   `TankbookRepository` a bulk upsert, a range/all fetch, and a **prune older than ~2 years**
   (`docs/SCHEMA.md`: "keep ~2 years rolling"), and let a `RateStore` be built from persisted rows
   and persist what it merges. Seed rows and fetched rows live in the same table; a fetched row for
   the same key replaces the seed row.
4. **`MoneyBackfillService`** (core, new file under `Rates/`): one pass over the money-bearing
   entries of the repository – **all four `Entry` types** – that
   - selects only those where `money.isRatePending`,
   - resolves the snapshot **on that entry's own `date`**, never today, never the fetch date,
   - writes **only** when `homeAmount` is nil (go through `Money.converted(using:)`, which already
     enforces this – do not hand-roll a second path),
   - persists with the ordinary **`.dirty`** sync state so the filled snapshot travels to the other
     devices (S8),
   - leaves everything else untouched, and is **idempotent** – a second pass writes nothing,
   - returns a small result value (filled count, still-pending count) with **no domain values in
     it**.
5. **The manual-rate path on the model.** A `Money` API that applies a user-supplied rate for the
   entry's date, sets `rateSource = .manual`, and – unlike the feed path – **replaces an existing
   snapshot**, because that is a user decision (hard rule 13, F9). It must be a **separate,
   explicitly-named entry point** from `converted(using:)`; a shared "force" flag on the feed path
   is how this rule gets broken later. A manual rate must then **survive** any later feed backfill.
6. **Expose the pending count to the stats layer** so P5.2b can render F9's footnote ("3 entries
   pending rates"). The home-currency sums in `HomeStats`, `TrendsStats` and `LogStream` already
   skip a nil `homeAmount` correctly – add the **count of entries excluded** alongside the sum, in
   the value types those return. No copy, no view code, no strings.
7. **Wire the app's store** – `ios/App/Sources/ConfirmManual/ManualFillUpCurrencySupport.swift`
   holds `enum AppRates { static let store = RateStore(seed: …) }` with the comment "the fetcher
   lands with sync". Give it the persisted cache and the real fetcher, behind the app's configured
   base URL, with the refresh kicked off off the launch path (never launch-blocking, hard rule 1).
   **This is the only `ios/App/` file you may touch, and you may add no strings to it.**

## Tests

`cd ios && swift test` is **642** right now (verified on `main`, exit 0). Run it first, record the
real number, and it must rise. Use the real in-memory GRDB repository, not a mock.

1. **Exact `Decimal` decode**: a pack body containing `4.2706` decodes to
   `Decimal(string: "4.2706")` **exactly**, and so does a long-tailed rate such as `0.0108384`.
   Assert equality against the string-built `Decimal` – a test that only checks
   `abs(a - b) < 0.0001` passes under the broken decode and proves nothing.
2. **Carried-forward source mapping**: all four of `"ecb"`, `"cis"`, `"ecb:carried-forward"`,
   `"cis:carried-forward"` map to the right `RateSource`, from **both** the seed decoder and the
   pack decoder. `"cis:carried-forward"` → `.cis` is the case that is broken today.
3. **Query construction**: the request URL carries `from`, `to` and `base` as the server expects,
   with dates as `yyyy-MM-dd`.
4. **The allowlist still gates it**: a fetch against a non-allowlisted host throws and **the
   transport is never called** (assert the double recorded zero requests, not just that it threw).
5. **Every failure is silent**: transport error, `500`, a 400 problem+json body, and a malformed
   body each leave the cache **unchanged** and the entries still pending, with nothing thrown out
   of `RateStore.refresh()`.
6. **Persistence round-trip**: merged rows survive a store rebuilt from a repository re-opened on
   the same database file (`CarSelectionTests` shows the two-repository pattern); the prune drops a
   row older than the window and keeps one inside it.
7. **`rateDate` is the ENTRY date.** Backfill an entry dated well in the past with a "today" set
   far away from it, and assert `rateDate` equals the entry's day. **The entry date must not be
   today** – with today's date the test passes even if the code uses "today", which is the exact
   defect F9 names as worse than no rate.
8. **Backfill never recomputes a written snapshot**: an entry already holding a snapshot is
   byte-identical after a pass in which the cache holds a **different** rate for that pair and day.
   A test where both rates are equal proves nothing.
9. **A manual rate replaces a feed snapshot** and sets `rateSource = .manual`; a **subsequent**
   backfill pass with a feed rate for that pair and day leaves the manual value untouched.
10. **Backfill marks the record dirty**, so the filled snapshot syncs (S8).
11. **Idempotence**: two passes leave exactly one write. Assert the second pass filled **zero** and
    that nothing about the records changed; a single-pass test is vacuous here.
12. **All four `Entry` types** are backfilled, not just `FillUp`.
13. **Derived stats follow** (hard rule 2): the vehicle's all-in cost/km, computed before and
    after a backfill pass, changes by the filled amount – computed independently in the test.
14. **The pending count is real**: with N pending and M converted entries, the stats value reports
    N and its home-currency sum equals the sum of the M converted `homeAmount`s **written out
    literally in the test**, not recomputed by the same expression the production code uses.

### Vacuous-assertion traps named for this task

- Asserting the fetcher "returned 3 rows" without asserting a decoded `Decimal` is exact (trap 1).
- A backfill test whose entry is dated **today**.
- A "never recompute" test whose second rate equals the first.
- An idempotence test that runs one pass.
- A pending-count test that computes the expected value with the same `reduce` the code uses.
- Asserting only that a call did not throw. `#expect(true)`. A "tamper" test mutating a field the
  code never reads.
- Mocking `TankbookRepository`. Use `TankbookDatabase.inMemory()`.
