## What this is, and the rule it must NOT be confused with

`docs/SYNC.md` → Reference data, verbatim:

> The vehicle catalog is **curated on the server**, and the server is the **master copy**. … This is
> a *different channel from user-data sync*, and conflating the two is the mistake to avoid.
> Nothing here has an SCN, a tombstone, a dirty queue or a conflict state, because the flow is
> **one-way and read-only**: the server publishes, the device consumes.

**Hard rule 9 says the server validates payload *structure*, never domain *meaning* - and it does
not restrain you here.** That rule governs **user payloads** travelling through sync, where the
server must never read what a field means. The vehicle catalog is **server-owned reference data**
that the server itself curates and publishes. Validating a catalog pack against its schema before
publishing it is therefore correct and required, not a rule-9 violation. (Read this paragraph
before deciding to refuse any part of the task. A previous agent correctly refused a rule-9
violation in P4.10, and it was right to; this is not one. If you still believe some specific part
crosses the line, say which part and why in your report rather than silently skipping it.)

## The contract, verbatim from `docs/API.md`

| Endpoint | Auth | Contract |
|---|---|---|
| `GET /catalog?since_version=` | **public** | Vehicle catalog delta or full pack + `packVersion`. ETag'd. |

`docs/SYNC.md` → "Applying an update", verbatim, and every clause is a requirement:

> - **Delta by default**: the client sends the `packVersion` it holds; the server answers with the
>   entries changed since, or a **full pack when the delta would be larger or the client is too far
>   behind**. `ETag` / `If-None-Match`, so an unchanged catalog costs a `304`.
> - **Validated before it is applied, whole or not at all.** A pack that fails its schema is
>   rejected entirely and the previous cache stands.
> - **`packVersion` is monotonic**: a pack older than the one held is ignored (rollback protection).

Shared conventions that apply: JSON bodies, camelCase, ISO-8601 UTC, RFC 7807 problem+json for
errors, `429` with `Retry-After` for rate limits.

## What to build

1. **The publish/curation path** into `vehicle_catalog`. It is an operator surface, not a public
   one - **do not expose it unauthenticated**, and say in your report how you gated it (an admin
   token from configuration, following how the project already holds server-side secrets, is
   fine; inventing a new user-facing auth flow is not).
2. **Monotonic `packVersion`, enforced.** Publishing a version **not greater than** the current one
   is **refused**. This is rollback protection and it is the rule most likely to be implemented as
   `>=` by accident.
3. **Schema validation at publish time.** A pack that fails its schema is refused **whole**, and
   **never served**. The previously published pack must still serve afterwards, untouched.
4. **`GET /catalog?since_version=<n>`**, public:
   - **delta**: only entries with `pack_version > n`, plus the current `packVersion`;
   - **full pack** when the delta would be larger than the full pack, or the client is too far
     behind. **You choose the threshold and state it in your report** - but it must be a stated
     rule with a test on **both** sides of it, not an accidental one;
   - **`ETag` + `If-None-Match` → `304`** when the catalog has not changed;
   - a missing/invalid `since_version` answers per the conventions (a `400` problem+json, or a
     documented default of "full pack" - state which and why).
5. **Answer honestly when there is nothing.** An empty catalog, or a `since_version` at or above
   the current version, gets a truthful answer (an empty delta with the current `packVersion`, or a
   `304`) - **never an invented entry and never a silent full pack pretending to be a delta**.

## Tests (L2, against real Postgres via Testcontainers)

`cd backend && dotnet test` is **211** as last recorded. **Run it first, record the real number**,
and it must rise.

1. **Delta returns only what changed**: seed at least **three** versions so a delta and a full pack
   are genuinely different sets, then assert the delta's entries **by identity**, not by count
   alone.
2. **Full pack when the delta would be larger**, and **delta when it would not** - both sides of
   your stated threshold. A test of one side passes an implementation that always returns a full
   pack.
3. **`304` on a matching `If-None-Match`**, **and** `200` with the body when it does not match.
   Assert both halves: a test of only the `304` passes an endpoint that always answers `304`.
4. **A pack failing its schema is refused at publish time** - and then **query the endpoint** and
   assert the **previous pack still serves unchanged**. A test that only asserts the publish call
   returned an error proves nothing about what is being served.
5. **Publishing `packVersion` ≤ current is refused**, and the stored pack is unchanged. Test the
   **equal** case as well as the lower one - `>=` vs `>` is exactly the likely bug.
6. **`GET /catalog` is reachable with no bearer token**; the curation path is **not**.
7. **The new migration applies and rolls back.**
8. **A `since_version` at the current version** returns the documented empty/`304` answer.

### Vacuous-assertion traps named for this task

- Asserting a `200` without asserting the entries in the body.
- A delta test with only two versions, where the delta and the full pack are the same set.
- Testing `304` without the `200` path (see 3).
- A schema-rejection test that never re-queries the endpoint (see 4).
- Testing `packVersion` rollback with only a *lower* version, never the equal one.
- Mocking the repository and asserting the mock. These are L2 tests against real Postgres.
- `Assert.True(true)`, or asserting only that a call did not throw.
