## The gap, found independently from both ends

`docs/SYNC.md` → Reference data, verbatim:

> **On overlap, the server wins.** A cached entry with the same identity as a server entry is
> replaced, not merged … **Entries the server no longer publishes are dropped on a full pack.**

**That last clause is unimplementable against the wire as shipped.** `GET /v1/catalog` answers
`{ packVersion, entries[] }` with **no delta-vs-full marker and no tombstone**, so a client cannot
tell *"here is everything"* from *"here is what changed"*. The two agents who built the halves
reported the same thing from opposite directions, neither having seen the other's work:

- **P5.6 (server):** *"Entry removal is not representable: `vehicle_catalog` is one row per `id`
  with no tombstone column, so a pack cannot express 'this entry no longer exists'."*
- **P5.7 (client):** *"The shipped wire has no delta-vs-full marker, so every pack is consumed as
  an identity overlay. A fresh client lands exactly on the server's set; a very-stale client
  receiving a full pack can retain a server-removed entry from its older cache."*

**Know the blast radius before you design, because it should keep the fix small.** Nothing is
corrupted and **no saved `Vehicle` is ever affected** - catalog values are *copied* into the
`Vehicle` row at Add-car time and no `Vehicle` references a catalog entry by id
(`docs/SCHEMA.md` → Vehicle catalog). So the defect is **a withdrawn model still being offered as
an Add-car suggestion on a stale device**. Wrong suggestions, not wrong data. Do not build a
migration, a repair pass, or anything that touches a garage.

## What already exists – build on it, do not redesign

- `ios/Sources/TankbookCore/Catalog/VehicleCatalogUpdater.swift` – `apply(pack:)` and the resolved

## What to build

1. **Say which kind of pack it is.** Add an explicit marker to the response - the shape is yours,
   but it must be **unambiguous and present on every response**, not inferred from a count or from
   the absence of a parameter. State the shape in your report.
2. **Make a removal expressible.** Two designs are defensible and you choose, **stating why**:
   - a **full pack is authoritative** - the client replaces its held set with it, so an entry that
     is absent is removed; or
   - an explicit **removed-ids list** alongside `entries`.
   The first matches `SYNC.md`'s existing sentence and needs no schema change; the second is
   cheaper for a stale client but adds a concept. **Do not implement both.**
   If your choice needs the server to remember what it withdrew (a tombstone or a soft-delete
   marker), that is migration **012**.
3. **Client: a full pack REPLACES, a delta OVERLAYS.** This is the behaviour change, and it is one
   branch in `apply(pack:)`. The bundled seed remains layer 1 underneath (hard rule 1: with no
   cache and no network, Add-car suggestions still work).
4. **Update `docs/API.md` and `docs/SYNC.md` in the same change.** `API.md` is a **breaking-change
   review point** - the response shape changes for a consumer that already shipped - so say so
   **loudly** in your report, and note that the only consumer is this repo's own client, which you
   are changing in the same commit.
5. **Backward tolerance, decided deliberately.** A client built before this change ignores an
   unknown field and keeps overlaying - which is exactly today's behaviour, so it degrades to the
   current bug rather than to something worse. **Confirm that is true of your shape** and say so;
   if it is not, change the shape.

## Tests

the real numbers, and both must rise.

**Server (L2, Testcontainers against real Postgres):**

1. **A full pack is marked full and a delta is marked delta** - assert the marker on both, from the
   same endpoint, in one test. A test of one side passes an implementation that hard-codes it.
2. **Publishing a pack that drops an entry is expressible**, and a subsequent full pack does not

3. **The existing contract still holds**: `304` on matching ETag, monotonicity refuses equal and
   lower, schema rejection still refuses whole and the previous pack still serves.
4. **Migration 012 applies and rolls back**, if you add one.

**Client (L1):**

5. **A full pack replaces**: a client holding a cached entry the server has withdrawn no longer
   offers it as a suggestion after applying a full pack. **Assert the suggestion is gone**, not
   just that the entry count changed.
6. **A delta still overlays**: a delta does **not** remove entries the client holds and the server
   did not mention. This is the test that stops "replace" being applied to everything.
7. **The stale-client path converges**: a client several versions behind, receiving a full pack,
   ends on **exactly** the server's set - not a superset.
8. **Hard rule 1 is intact**: no cache, no network - the bundled seed still answers.
9. **The garage is still untouchable**: the byte-identical saved-`Vehicle` test still passes.

### Vacuous-assertion traps named for this task

- **Testing removal only from an empty cache.** That path already works today and proves nothing
  about the bug - test 7 exists precisely because the stale client is the broken case.
- Asserting entry **counts** rather than that a specific withdrawn model stopped being suggested.
- Marking every response "full" - test 1's two halves exist for that.
- Implementing both designs from step 2 "to be safe".
- Loosening the monotonicity guard or the schema validator to make a new test pass.
- `Assert.True(true)` / `#expect(true)`, or asserting only that a call did not throw.
