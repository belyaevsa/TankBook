## What to build

1. **Evaluate at launch and on foreground**, against the config snapshot the app already holds
   (live, else cache, else bundled) - **never** against a fetch in flight. A cold start with no
   cached document shows nothing, which is correct.
2. **`.recommended` (soft)**: a dismissible row in Settings -> About. Quiet. It is information, not
   an interruption.
3. **`.required` (hard)**: a non-dismissible notice **on the server-backed surfaces only** - sync,
   cloud extract, import parse. It names its next step (hard rule 7).
4. **Nothing else changes.** Under `.required` the user can still log a fill-up, edit it, see
   consumption recompute and export - offline, indefinitely. **This is hard rule 1 and it is the
   whole point of the design.**

## The App Store link problem, and the honest answer

There is **no App Store listing and no app id yet**. So there is nowhere to send the user.

Do **not** invent a URL, do not link to a placeholder, and do not show a button that does nothing.
Mirror what the marketing site does in the same situation: state the situation plainly and give the
real next step that exists today. Put the store link behind an app-id value that is currently empty,
so the button appears only when there is somewhere for it to go - the same shape as the site's
`apple-itunes-app` gate.

## Vacuous-test traps, named

- Asserting the notice's **text** rather than that the local path still works. The defect this task
  guards against is a screen refusing to save, not a missing label.
- A UI test that asserts a button `isEnabled` - XCUITest reports elements hittable that a save bar
  is covering, and `isHittable` does not model occlusion on this project.
- Seeding `.required` in a way that also disables sync for an unrelated reason, so the test passes
  whatever the code does.
