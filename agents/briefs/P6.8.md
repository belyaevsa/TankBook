## The rule, and the distinction the whole task turns on

`docs/SYNC.md` → **Low Power Mode** is the authority. Verbatim:

> **The load-bearing distinction is background vs user-initiated.** A deferral policy that cannot
> tell them apart will postpone a restore or a "sync now" tap, and a user staring at a spinner that
> was silently cancelled has no next step (hard rule 7) and reads as a hang.

| Defers while Low Power Mode is on | Never defers |
|---|---|
| Opportunistic sync cycles (launch, foreground, timer) | Any **save** - always local, always immediate |
| Attachment/blob **upload** and **prefetch** | A sync, restore, export or retry the **user asked for** |
| Rate pack refresh (`RateStore.refresh`) | Capture, OCR and the confirm sheet |
| Vehicle catalog pack fetch | An already-scheduled local notification |
| Any repeating timer job | Reading, editing and deleting - the whole local app |

Three more clauses from that section, each of which is a way this gets built wrong:

- **iOS already disables Background App Refresh in Low Power Mode.** Do not duplicate that and do
  not rely on it: the gap the app closes is **foreground opportunistic** work.
- **Resume on `NSProcessInfoPowerStateDidChange`, not at next launch** - a device that left the
  mode hours ago must not still be holding its queue.
- **The power state is an injected value, never `ProcessInfo` read inline.** A policy that reads
  the device directly cannot be tested, and this policy's entire content is *when it says no*.
  Precedents: `TabBarMetrics`, `PumpPhotoGate`.

## What already exists

- `ios/Sources/TankbookCore/Sync/SyncCoordinator.swift`, `SyncEngine.swift` – the cycle to gate.
- `ios/Sources/TankbookCore/Sync/BlobUploader.swift`, `BlobPushGate.swift` – the upload path;
  `BlobPushGate` is the **existing precedent for a gate that defers without losing data** (returning
  false leaves the record dirty for a later cycle).
- `ios/Sources/TankbookCore/Rates/RateStore.swift` → `refresh()`; `Catalog/VehicleCatalogUpdater.swift`
  → `refresh()`. Both are opportunistic fetches.
- `ios/Sources/TankbookCore/Config/PumpPhotoGate.swift` – a policy as a value in core.

## What to build

1. **An injected power-state seam** (a protocol with a test double and a real
   `ProcessInfo`-backed implementation), plus a **pure policy value** that answers, for a given
   work kind and trigger, whether it runs now or defers.
2. **Gate the opportunistic paths** listed above on it - and leave the user-initiated ones alone.
   The trigger (background vs user-initiated) must be **explicit at the call site**, not guessed.
3. **Resume**: observe `NSProcessInfoPowerStateDidChange` and drain what was deferred.
4. **Nothing is lost.** A deferred cycle leaves the dirty queue exactly as it was - the same
   property `BlobPushGate` already has.

## Tests

`cd ios && swift test` is **742**. Run it first, record the real number, and it must rise.

1. **With the state ON, an opportunistic cycle defers** and the dirty queue is **unchanged, nothing
   dropped** (hard rule 8) - assert the queue, not just the return value.
2. **With the state OFF, the same cycle runs.** Without this half, an implementation that always
   defers passes test 1.
3. **A user-initiated sync/restore RUNS while the mode is on.** This is the test the naive
   implementation fails, and it is the reason the task exists.
4. **Resume fires on the power-state change, not only at launch**, and the deferred work then
   drains.
5. **A save, an edit and a delete are unaffected** while the mode is on.
6. **Blob upload/prefetch defers without losing the pending record.**

### Vacuous-assertion traps named for this task

- **A gate consulted but not awaited** - the subtlest form, and it has shipped here before (P4.6).
- Testing the defer path without the run path (test 2).
- Asserting only that the power state was *read*.
- A test that reads the real `ProcessInfo` and therefore only passes on the machine that ran it.
- `#expect(true)`, or asserting only that a call did not throw.
