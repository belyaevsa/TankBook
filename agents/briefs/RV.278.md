# RV.278 - the expense corpus scores the photograph, not the dump

**Scenario: J7b · the shop receipt.** Product owner, 2026-09-13, on seeing `RV.277`: *"expected is
better to have an image as an input, rather than recognised data."*

`RV.277` made `expenses/` a ratcheted gate class, but `CorpusExpenseScorer` reads the `.txt` beside
each `.jpg` as the INPUT. That dump was produced by Vision once; a Vision change (a new iOS
runtime, a different rendition size) can never move the expense number, while the fuel classes
(`receipts/`, `pump/`) OCR their photographs at test time. The dump is a debugging artefact.

## Build

- Where a `.jpg` exists, the scorer AND the spike run Vision on it - the same OCR path the fuel
  classes use (`CorpusABScorer` / the receipts scorer; reuse it, never a second OCR call site) -
  and score the extractor's output against `expected.csv`.
- The `.txt` beside a photo is regenerated by `--dump-text` and compared with the committed
  one: a difference is reported as **drift** (the OCR changed), never scored. Hand-authored
  `.txt` fixtures with no photo keep scoring the text - they are the input by construction.
- `expenses/README.md` and `fixtures/README.md` say which file is the input for which fixture.
- Cost: two photos today; say what the class costs in `swift test` seconds before and after.

## Tests

- **L1**: the two Tallinn photographs score through Vision and match `expected.csv`
  (kind, total, currency, date); the ratchet stays at 29/29 or the difference is explained in
  `HIGH-WATER.md`.
- **L1**: a stale `.txt` beside a photo is reported as drift, not scored.
- `swift test` in full; the spike over `fixtures/expenses` prints the same class line.

## Mutation - named

Score the `.txt` again for a photo fixture whose committed dump you hand-break; the drift check
goes red (and the score must NOT change, proving the text was not the input). Verbatim.
